# AI-LOG-001: AI 세션 기록 환경 구성 최종 계획

> 상태: 단일 feature 작업과 develop 로그 전용 커밋의 master 동기화를 반영한 계획. 구현 전 사용자 확인 대기. 이 문서가 이전 계획과 보완안을 대체한다. 이번에는 이 문서만 수정하며 구현, 다른 파일 생성, hook 설치, Git 설정 변경, 스테이징, 커밋, 병합, push를 하지 않는다. 아래 실행 검증은 구현 후 수행할 계획이며 아직 통과한 결과가 아니다.

## 0. 목표와 확정된 작업 흐름

프로젝트의 모든 AI 세션을 자동 기록하고 원본 전체를 저장소의 `ai-logs/`에 제출한다. 계획·조사·구현·테스트·실패·수정·재개·로깅 정책 변경도 포함하며, 마스킹 외에는 원본을 편집하지 않는다. 소스코드·작업 ID·브랜치·정책·폴더 구조가 바뀌어도 기존 기록을 보존한다.

**동시에 수정하는 feature는 하나다. develop에서는 검토·검증만 하고 기능 수정은 feature에서 한다.** 검토가 끝나면 로그 내역만 별도 커밋으로 만들고, 해당 로그 전용 커밋만 master에 자동 동기화한다. 보완 작업은 최신 master를 feature에 병합한 뒤 진행한다.

```text
master → feature 생성 → 구현·테스트 → develop에 병합·리뷰 검증
                                         │
                                         └─ 로그 전용 커밋 → master에 해당 커밋만 반영·게시
                                                                  │
                         보완 필요: feature ← 최신 master 병합 ←──┘
                                     │
                                     └─ 보완 → develop 재병합·재검증 → 로그 게시 반복

기능 검증 통과: feature → master 일반 merge(--no-ff)
```

리뷰 로그 전달은 `cherry-pick`으로 해당 로그 커밋의 변경만 적용하고, **기능 코드 반영은 검증된 feature의 일반 merge로 수행**한다. 이 두 작업을 구분한다. develop 전체를 master에 병합하지 않는다.

**로그는 프로젝트 전체 기록이다. 이전 feature나 검증 작업의 대화가 master 로그에 포함되는 것은 정상이며, 로그 전용 동기화로 해당 기능 소스가 들어가지는 않는다.** 로그 게시 전후 master의 비-로그 파일이 동일한지 검증한다.

## 1. 범위와 운영 결정

- 신규 feature는 항상 master에서 생성한다. AI는 feature 작업·검증과 develop 통합 검증을 담당한다. 사용자가 시작한 리뷰 게시 명령은 검증된 로그 전용 커밋의 master 반영·push를 자동 수행할 수 있다. 기능 코드의 master 병합은 검증 통과 후 사용자가 별도로 시작한다. AI가 이 절차 밖에서 master 갱신·push를 임의 실행하지 않는다.
- 로그 수집·마스킹·검증·단계 스냅샷·로그 전용 커밋·master 로그 동기화·보완 전 기준 갱신은 자동 처리한다. 사용자는 프로젝트의 리뷰 게시 동작이나 기능의 master 병합을 시작하며, 로그 복사·sync·스테이징·cherry-pick 순서는 관리하지 않는다.
- develop의 리뷰 결과는 로그 전용 커밋으로 분리하고, 리뷰 게시 명령이 그 커밋만 master에 자동 cherry-pick한다. 여러 feature를 순회하지 않는다. 보완 작업을 재개할 때 현재 feature가 최신 master를 받아 로그를 이어간다.
- Git 커밋 hook은 읽기 전용 검사만 한다. sync·마스킹·스냅샷 생성은 커밋과 분리된 자동 단계다. 마지막 응답 뒤의 원본 꼬리도 최종 병합과 pre-push 검사에 포함한다.
- 어느 등록 세션이든 턴이 진행 중이면 현재 작업 폴더의 **Git 변경 작업**은 보류한다. 상태 조회·diff 등 읽기 전용 Git 명령은 가능하다. 소스 커밋·브랜치 전환·병합·단계 로그 커밋은 모두 보호 대상이다.
- 상주 감시기, AI CLI 실행 래퍼, 별도 worktree 생성, staging 브랜치, amend, 매 턴 커밋, 브랜치 순회 동기화는 사용하지 않는다. Python 표준 라이브러리 기반의 유한한 hook·작업 명령을 사용한다.
- Claude `cleanupPeriodDays` 설정은 최대 3일의 과제 범위에서 제외한다. 별도 gitleaks 검사는 선택 사항이다.
- 서비스명 `AI`, 작업 ID `LOG-001`(로깅 환경), `LOG-002`(최종 제출 검증)는 제안값이며 실제 식별자는 확정이 필요하다. 단계 로그 커밋은 해당 작업 ID를 사용한다.
- 구현은 ① 기본 제출 요건 확보 → ② 단계 스냅샷·턴 보호 → ③ 리뷰 로그 게시·보완 재개·master 기능 병합·pre-push의 세 단계다. 기존 작업 스크립트의 명령으로 묶고 별도 서비스·로그 브랜치·상주 프로세스는 만들지 않는다. 각 단계 검증 후 다음 단계로 간다.

## 3. 수집 대상·탐색·세션 등록

- 두 도구의 이 프로젝트 전체 세션을 수집한다. 실패·중단·재개·계획 검토 세션을 포함하고 다른 프로젝트는 제외한다.
- 세션 판정은 폴더명만으로 하지 않고 기록 안의 cwd와 등록 정보로 한다. 프로젝트 루트·하위 폴더 및 `git worktree list`에 이미 등록된 경로를 포함하되 이 작업에서 worktree를 새로 만들지는 않는다.
- Claude 프로젝트 폴더명에서 `_` 등이 `-`로 변환되면 다른 경로와 충돌할 수 있다. 폴더 하나가 일치한다고 그 안의 모든 최상위 세션을 무조건 포함하지 않는다. 각 세션의 cwd를 확인하고, 하위 파일은 확인된 부모 세션에 연결한다.
- Claude는 최상위 `<session-id>.jsonl`과 대응 `<session-id>/` 폴더 전체를 수집한다. `subagents/`, `tool-results/` 및 그 밖의 세션 부속 파일도 파일 목록에 기록한다. 링크를 따라 다른 프로젝트·인증 파일까지 수집하지 않는다.
- Codex 서브에이전트의 별도 rollout도 수집한다. 자식에 cwd가 없으면 부모 세션 연결·등록 근거로 판정하며, 판정 불가 파일을 조용히 제외하지 않고 보류 상태로 남긴다.
- 두 도구의 SessionStart hook이 Git 제외 `.ai-logging/` 등록 파일에 도구, 세션 ID, 원본 경로, cwd, 브랜치, 시작 시각을 기록한다. 세션 ID는 도구와 함께 식별하며, 브랜치는 관찰 정보일 뿐 수집 필터가 아니다.
- 등록 목록은 덧붙여 유지한다. 재개나 경로 변경을 기록해도 과거 연결을 지우지 않는다. 원본이 사라지거나 탐색에서 빠지면 기존 사본을 삭제하지 않고 해당 세션을 미확인 상태로 유지한다.
- 프로젝트 이동·이름 변경 시 동일 프로젝트임을 확인한 이전 루트 경로를 등록 목록에 유지한다. 과거 worktree가 목록에서 사라져도 이미 등록한 세션을 잊지 않는다. 경로 충돌은 사용자 확인 없이 합치지 않는다.
- hook은 세션 시작 시 로드되는 것을 운영 기준으로 삼는다. 설치 전·변경 전 세션에 자동 적용됐다고 가정하지 않는다. 위 Codex·Claude 세션과 이후 세션은 소급 탐색해 등록·수집한다.
- `AGENTS.md`에 세션 저장을 끄는 `codex exec --ephemeral`, `claude -p --no-session-persistence`, Codex archive, `--dangerously-bypass-hook-trust` 사용 금지를 명시한다.
- 로컬 원본이 남지 않는 Codex 클라우드 작업, Claude Code 웹, 원격 에이전트, 예약 작업, 웹 채팅, 별도 IDE 내장 AI는 기본 사용을 금지한다. 현재 확인된 Codex VS Code 확장은 로컬 원본이 있는 사용 방식이다. 예외 도구가 꼭 필요하면 도구별 전체 원본 내보내기·수집·검증 방법을 먼저 확인하고 `ai-logs/`에 포함한다. 요약본만 가능한 경우 동등한 증거로 인정하지 않는다.

## 4. 자동 수집과 턴 상태 보호

### 4.1 hook 역할

| 이벤트·실행 지점 | 자동 처리 |
| --- | --- |
| 두 도구 SessionStart | 세션·원본·cwd·브랜치 등록, 기존 세션 소급 탐색, hook 적용·상태 확인 |
| 두 도구 UserPromptSubmit | 해당 세션의 턴 진행 상태를 원자적으로 등록한 뒤 턴 시작 허용 |
| 두 도구 Stop | 해당 턴 종료 상태 기록, 두 도구 전체 프로젝트 원본 sync, 예약된 단계 로그 처리 가능 여부 확인 |
| Claude SessionEnd | 마지막 원본·부속 파일 수집, 상태 대조. 근거 없이 진행 중 상태를 해제하지 않음 |
| feature/develop 작업 단계 완료 | 현재 브랜치에 스냅샷·로그 커밋 예약. 모든 턴 종료·빈 index 조건에서만 실행 |
| 사용자 리뷰 게시 명령 | 전체 로그 확정 → 로그 전용 커밋 검사 → master에 해당 커밋만 반영 → develop/master 게시 |
| feature 보완 작업 재개 | 게시된 master를 확인하고 현재 feature에 일반 merge한 뒤 source 작업 재개 |
| 사용자 master 기능 병합 명령 | 모든 턴 종료·깨끗한 작업 폴더·develop 검증 이력 확인 후 남은 최종 로그와 feature 병합 |
| master pre-push | 실제 push 대상 커밋의 전체 로그 완전성을 읽기 전용 검증 |

- 일반 Stop은 수집을 수행하고, 작업 완료로 등록된 단계만 로그 커밋한다. Stop이 테스트 완료를 추측하거나 매 턴 커밋하지 않는다.
- AI가 턴 안에서 요청한 Git 변경 작업은 즉시 실행하지 않고 예약한다. 모든 등록 턴이 종료된 뒤 같은 작업 폴더에서 실행한다. 계획 확인 후의 구현은 이 실행 경로를 사용하며 raw Git 변경 명령으로 우회하지 않는다.
- 필요한 브랜치 전환은 턴이 끝난 명시적 작업 단계·리뷰 게시 명령에서만 한다. 일반 수집 hook이 다른 브랜치를 순회하지 않는다. Git pre-push 안에서 master를 수정하거나 재귀적으로 push하지 않고, 게시 명령이 먼저 작업한 뒤 읽기 전용 pre-push 검증을 거친다.

### 4.2 세션별 턴 상태

- `.ai-logging/`에 세션 ID, 도구, 턴 ID 또는 상관관계를 확인할 수 있는 세대 값, `active/idle/unknown`, 갱신 시각을 저장한다.
- UserPromptSubmit은 active로 기록한다. Stop은 대응하는 턴만 종료한다. 과거 Stop이 늦게 도착해 새 턴의 active를 지우지 않도록 한다. 동시 턴·중복 이벤트도 구분한다.
- hook 누락·비정상 종료·상태 손상·설치 전 세션은 unknown으로 취급하고, 원본의 종료 이벤트와 실행 상태로 확인한 뒤에만 idle로 확정한다. 시간 경과나 파일 크기 정체만으로 idle을 추정하지 않는다.
- 세션별 원본 탐색과 등록 목록을 매번 대조해 미등록 프로젝트 세션을 놓치지 않는다. active 또는 unknown이 하나라도 있으면 Git 변경·최종 제출을 진행하지 않는다.
- UserPromptSubmit과 Git 변경 작업은 같은 보호 잠금으로 조정한다. 턴 확인 직후 새 프롬프트가 시작되는 경쟁을 막기 위해 Git 작업이 보호 구간을 잡은 동안 새 턴 시작을 기다리게 한다.
- **수집 hook의 오류는 exit 0으로 모델을 반복 실행시키지 않는다. 다만 UserPromptSubmit의 턴 보호는 별도 안전 규칙이다.** 보호 잠금·active 등록을 확보하지 못한 프롬프트를 진행시키면 요구한 Git 보호를 보장할 수 없으므로 시작을 보류하거나 안전하게 거부한다. 설치 버전에서 실제 차단·대기 동작을 시험한다. Stop에서 exit 2로 모델을 계속 돌리는 방식은 사용하지 않는다.
- 이 보호는 구성한 로컬 도구·작업 명령에 적용된다. 임의 외부 프로세스의 Git 조작까지 잠글 수 있다고 주장하지 않으며, 작업 전후 HEAD·index·상태 변화를 재검사한다.

### 4.3 sync·예약·공유 index

- 전체 탐색 → 원본 읽기 → 마스킹 → 파일·원본성·민감정보 검증 → 성공본 공개 순서다. 검증 실패 시 이전 통과본을 보존하고 이번 갱신을 보류한다.
- 동시 sync와 단계 처리는 파일 잠금·제한 시간·실행 상태로 관리한다. 중간 종료 후 마지막 완료 세대를 식별하고 재실행할 수 있게 한다.
- 단계 로그 커밋은 모든 등록 턴이 idle이고 **공유 index에 기존 스테이징 변경이 없을 때만** 한다. 수정·미추적 소스가 있어도 그 내용을 스테이징하지 않는다. 예약된 브랜치·HEAD가 달라졌거나 Git 작업이 진행 중이면 보류한다.
- 자동화가 만든 스냅샷만 한정해 스테이징하고 index의 실제 경로·내용을 다시 검증한다. `git add -A`, 자동 stash, 강제 checkout/reset으로 사용자 변경을 처리하지 않는다.
- 같은 단계는 한 번만 완료 처리한다. 자기 hook·Git 처리의 새 로그 때문에 새 단계를 등록하는 무한 커밋을 막는다. 이후 꼬리는 다음 수집·최종 병합 단계가 처리한다.
- 잠금·턴·index 때문에 미뤄진 작업은 다음 Stop 또는 명시적인 작업 실행 시 재시도한다. 상주 재시도 프로세스는 두지 않는다. 최종 병합은 보류를 성공으로 처리하지 않는다.
- 상태 진단에는 파일 식별자·줄 번호·규칙 종류만 기록한다. 원본 줄·민감값·그 값을 포함한 예외 원문은 출력하지 않는다.

### 4.4 설정과 신뢰

- Codex는 `.codex/hooks.json`, Windows는 `commandWindows`를 사용한다. 프로젝트 루트 기준으로 경로를 찾는다. `/hooks` 등으로 신뢰를 확인하고 설정 변경 후 재신뢰·새 세션 검증을 한다. trusted_hash 임의 생성·신뢰 우회는 금지한다.
- Claude는 `.claude/settings.json`에 이벤트와 민감 파일 deny를 설정하며 기존 설정을 보존한다.
- Git hook 검증만 믿지 않고 작업 명령도 같은 검증기를 호출한다. 중첩 호출의 잠금 교착·hook 재귀를 테스트한다.

## 5. 마스킹·민감정보 검증

### 5.1 치환 원칙

- 원본은 수정하지 않고 제출용 사본에서만 민감값을 `****`로 치환한다. 문장 수정, 줄 삭제, 순서 변경, JSON 재직렬화, 개행 정규화는 하지 않는다.
- 기본 치환 목록은 설치 단계에서 한 번 확정한다. 대상은 Claude `session_context` 첨부 이메일, `session-owner`의 `accountUuid`·`organizationUuid`, Codex `session_meta`의 `creator_account_id`·`creator_user_id`, 사용자 경로다. 실제 값은 Git 제외 파일에서 안전하게 읽으며 명령줄·대화에 출력하지 않는다. 기본 목록 확정과 전체 검증 통과 전에는 첫 스냅샷을 커밋하지 않는다. 이후 새 후보가 발견되면 자동 허용하지 않고 목록을 검토·갱신한다.
- 마스킹은 Git 제외 치환 목록과 알려진 토큰 형식에 의해서만 수행한다. 무작위 문자열 길이·엔트로피만으로 자동 마스킹하지 않는다.
- `signature`, `encrypted_content`, 일반 UUID·해시는 기본 자동 판정 제외 대상이다. 다만 **명시적으로 치환 대상으로 결정한 계정 식별자·개인정보는 구조 필드 예외보다 우선**한다. 구조 필드 예외를 모든 긴 문자열에 확대하지 않는다.
- 단순 `sk-` 검색에서 Codex 22건·Claude 23건이 잡혔으나 실제 키 형식은 0건이었다는 기존 오탐 사례를 테스트에 반영한다. 일반 단어·`task-` 등을 키로 판정하지 않는다.

### 5.2 마스킹보다 넓은 검증

- 검사 대상은 모든 이메일 형식, 알려진 토큰 형식, `password`·`Authorization`·`Bearer` 같은 키워드, 개인키 헤더, 구조 필드 밖의 긴 무작위 문자열이다. 키워드·긴 문자열은 후보를 찾는 근거이지 비밀이라는 단정이 아니다.
- 검출된 후보가 치환 목록이나 허용 목록으로 처리되지 않으면 보류한다. 사용자가 원본에서 안전하게 판단해 비밀이면 치환 목록, 비밀이 아니면 허용 목록에 추가한다.
- 허용 목록은 저장소에 포함할 수 있지만 검토한 비밀이 아닌 예제·규칙·문맥만 좁게 허용한다. `Authorization` 전체 무시 같은 광범위 규칙을 사용하지 않으며, 실제 비밀값을 허용 목록에 기록하지 않는다. 파일명과 세부 형식은 구현 전에 확정한다.
- 치환 목록 값이 사본에 평문 또는 JSON 이스케이프 형태로 남아 있으면 보류한다. 중첩 도구 인수의 여러 단계 이스케이프와 경로의 `\\`도 검사한다. 원본의 표현 자체를 정규화하지 않는다.
- 비밀값을 명령줄·프롬프트·진단 출력으로 전달하지 않는다. 검사 스크립트는 치환 목록 파일을 직접 읽는다. AI가 값을 대신 출력해 사용자에게 확인받는 방식도 쓰지 않는다.
- Claude 부속 파일에도 같은 검증을 적용한다. JSONL이 아닌 텍스트는 원본 인코딩·개행·바이트를 유지하고, 해석할 수 없는 바이너리·이미지·미지원 인코딩은 안전하다고 간주해 통과시키지 않는다. 사용자 검토 전 보류하며 임의 삭제·변환하지 않는다.

### 5.3 예방과 사람의 검토

- `.claude/settings.json`의 `permissions.deny`와 Codex 작업 규칙에 `~/.codex/auth.json`, `.env` 및 인증·개인 치환 파일의 불필요한 읽기 금지를 둔다. 수집기가 원본과 치환 목록을 내부적으로 읽는 것은 지정된 처리 경로로 제한하고 내용을 출력하지 않는다.
- 규칙 문서와 도구별 deny 설정만으로 모든 셸·MCP 접근이 차단된다고 주장하지 않는다. 실제 적용 범위는 가짜 민감 파일을 이용해 검증하며 실제 인증 파일을 읽어 시험하지 않는다.
- 이름, 내부 명칭, 주소 등 패턴만으로 판단할 수 없는 개인정보는 제출 전에 사람이 검토한다. 선택적으로 gitleaks 등으로 2차 검사한다.

## 6. 스냅샷 형식·원본성·최신본 판단

### 6.1 저장 구조

```text
ai-logs/
  live/                                      # 현재 전체 사본. 1단계 제출 대상, 2단계 이후 Git 제외
  snapshots/                                 # 2단계 이후 Git 추적
    <tool>/<session-id>/<policy-version>/
      L<20자리 원본 길이>-<sha256>/
        files/                               # 세션 원본과 부속 파일의 전체 마스킹 사본
        manifest.json                        # 해당 스냅샷의 불변 메타데이터
.ai-logging/                                 # Git 제외
  등록·턴 상태·잠금·치환 목록·예약·검증 결과·재개 상태·복구 보관본·파생 색인
```

- 스냅샷은 일부 턴이나 증분 조각이 아니라 **그 시점에 존재하는 해당 세션 원본과 부속 파일 전체**다. 최종 수집은 등록된 모든 세션에 이 규칙을 적용한다.
- 원본 내용·정책이 같으면 같은 경로·manifest를 생성한다. 브랜치명이나 실행 시각 때문에 같은 내용의 중복 스냅샷을 만들지 않는다.
- 확정 스냅샷은 일반 자동화에서 수정·삭제하지 않는다. 세션이 늘면 새로운 전체본을 추가한다. 공통 가변 `ai-logs/manifest.json`은 두지 않고 개별 manifest에서 전체 색인을 파생한다.
- develop의 리뷰 게시 시점에는 모든 세션의 최신 전체 스냅샷이 있어야 한다. master에 필요한 미반영 로그 전용 커밋만 자동 선택해 cherry-pick한다. feature는 보완 재개 시 master의 기존 스냅샷을 일반 merge로 이어받는다. 같은 내용의 스냅샷은 재생성하지 않으며 최종 기능 병합 시 그 뒤 늘어난 원본만 새 전체본으로 보완한다.

### 6.2 `L<원본 길이>-<hash>`의 정확한 의미

- `L` 뒤 숫자는 **마스킹 전 세션 원본 파일 묶음의 바이트 길이 합계**다. 주 JSONL과 모든 부속 파일을 포함하며 파일별 길이도 manifest에 기록한다. 고정 20자리 0채움을 사용한다. 예: `L00000000000000123456-<64자리 sha256>`.
- hash는 정렬된 원본 파일 목록·원본 해시·사본 해시·정책/스키마 버전에서 결정적으로 계산한다. manifest의 파생 ID·실행 시각을 자기 hash에 순환 포함하지 않는다. 비밀 치환값 자체는 manifest에 넣지 않는다.
- 정상적으로 덧붙는 동일 정책의 세션에서는 원본 길이가 증가하므로 이름순 마지막이 최신 전체본이다. 마스킹 후 길이, Git 커밋 시각, 타임스탬프 최댓값으로 최신본을 정하지 않는다.
- **같은 길이에서 다른 hash가 나오는 경우 hash의 사전순은 시간순이 아니다.** 동일 정책에서 이런 상태가 생기면 자동으로 최신을 선택하지 않고 원본 재작성·부속 파일 변동 등 원인을 검증해 보류한다. 파일 삭제·절단도 보류한다. 비슷한 길이를 임의 증가시켜 이름을 맞추지 않는다.
- 원본은 그대로이고 마스킹 정책만 바뀐 경우는 별도 policy-version 영역에서 전체를 다시 검증한다. 현재 적용 정책을 명확히 기록하고 이전 정책과 이름순으로 섞지 않는다. 기존 스냅샷에 민감정보가 발견되면 7절의 정정 절차를 따른다.
- README에는 **“세션별 이름순 마지막 스냅샷이 최신 전체본”**이라고 적고, 바로 이어 **현재 적용 정책의 영역에서 검증을 통과한 스냅샷 기준이며 동일 길이 불일치는 제출을 차단한다**는 조건을 적는다. 실제 제출은 이름만 믿지 않고 원본 해시·파일 목록까지 검사한다.
- 단일 파일이 50MB(50,000,000바이트)를 넘으면 정제된 파일 식별자·크기로 경고한다. 자동 잘라내기·요약·압축 변환·삭제는 하지 않는다. 경고 자체로 원본 보존을 포기하지 않는다.

### 6.3 원본성·완전성

- 마스킹 외에는 바이트 동일해야 한다. JSON 재직렬화·정렬·개행 변환은 하지 않는다. 시간 순서는 파일 내 줄 순서이며 타임스탬프 역전·없는 줄도 유지한다.
- live는 작성 중인 마지막 줄을 보류할 수 있지만 완결된 줄까지의 연속 앞부분만 수집한다. 단계 스냅샷은 읽은 시점의 파일 끝까지 완결된 경우에만 확정한다.
- 이후 원본이 늘어도 이전 원본 길이·해시로 앞부분 불변성을 확인한다. 동일 세션의 재작성·절단·뜻밖의 부속 파일 변경은 기존 증거를 보존하고 실패 처리한다.
- manifest에는 UTC, 첫 시각·마지막으로 등장한 시각, 파일 목록, 파일별 원본/사본 길이·해시, 줄 수 적용 여부, 정책·스키마 버전을 기록한다. 없는 시각을 만들거나 마지막 시각을 최댓값으로 바꾸지 않는다.
- 최종 검증은 모든 등록 세션의 **최신 원본 전체와 부속 파일**에 맞는 스냅샷이 대상 Git 커밋 안에 있는지 검사한다. 더 짧은 중간본, 작업 폴더에만 있는 파일, Git 제외 live만으로 통과시키지 않는다.
- 원본을 못 찾으면 목록에서 제거하지 않고 제출을 보류한다. 기존 보관 사본은 보존하지만 원본 대조 완료로 표시하지 않는다.
- 치환·허용 목록·검증 코드·스키마가 달라지면 전체 재검증한다. 증분 검사는 앞부분 불변성과 같은 정책이 확인된 경우만 사용한다.
- Codex exec 내부 명령 개수·의미를 재구성하지 않고 원본을 그대로 둔다. README에 중첩 exec 형식을 설명한다.

## 7. 정책·구조 변경에도 기록 보존

- 세션 등록 목록은 기존 내역과 새 내역의 합집합으로 유지한다. 현재 feature에 직접 관련 없는 대화도 같은 프로젝트면 수집한다.
- 소스 정리·폴더 이동·리팩터링으로 도구 원본, `ai-logs/`, `.ai-logging/`를 삭제하지 않는다. 전체 `git clean -fdx/-fdX`, 로그 대상 강제 checkout/reset/restore를 금지한다.
- `.ai-logging/retained/`에 마지막 통과본과 복구 자료를 보관한다. 브랜치를 바꿔 Git 파일 집합이 달라져도 등록 목록·로컬 보관본을 줄이지 않는다. 로컬 디스크 손실까지 막는 백업이라고 주장하지 않는다.
- 정책 변경은 버전을 올리고 원본 전체를 다시 검증한다. 과거 대화를 잘라내지 않는다. 폴더·manifest 변경은 전체 세션·파일·행·해시 비교와 이전 완료본 복구 절차를 먼저 마련한다.
- 1단계에서 2단계로 옮길 때에도 live의 모든 기록이 스냅샷에 바이트 기준으로 보존됐음을 먼저 확인한다. 제출 경로만 바꾸는 것을 로그 삭제로 처리하지 않도록 동등성 검증을 남긴다.
- 단계 커밋 이전부터 개인정보 기준을 적용한다. 이미 커밋한 비밀은 이후 마스킹 커밋만으로 과거 이력에서 없어지지 않는다. 발견 시 새 커밋·제출을 차단하고 사용자에게 정정 계획을 보고한다. 자동 amend·이력 재작성·push는 하지 않는다.
- 저장소 이동·새 clone에는 Git 제외 상태·치환 목록·보관본·로컬 원본 위치의 별도 이전이 필요하다. Git만으로 원본 보존이 자동 복구된다고 가정하지 않는다.

## 8. Git·검증·feature → master 병합

### 8.1 공통 커밋·브랜치 규칙

```text
[서비스-작업ID] 제목

  작업 내용
```

- source 커밋, 단계 로그 커밋, merge 커밋 모두 공통 형식을 사용한다. 기능의 master 반영은 일반 `merge --no-ff`, master의 로그 반영만 검증된 단일 부모 로그 전용 커밋의 `cherry-pick -x`를 사용한다. squash·rebase·amend는 사용하지 않는다.
- master에서 feature 생성 → feature 작업 → develop 검증 → 리뷰 로그만 master에 게시 → 보완 시 feature에서 최신 master를 병합하고 수정·재검증 → 성공 시 **같은 feature를 master에 병합**한다. develop 전체의 master 병합·feature 역병합은 하지 않는다.
- 신규 feature 생성 전 master의 로깅 설정·스크립트·Git 속성·hook 실행 상태를 확인한다. 없으면 “LOG-001을 master에 먼저 병합해야 한다”고 알리고 멈춘다. 최초 LOG-001만 예외다. 구현 단계별로 아직 만들지 않은 후속 단계 파일까지 요구하지는 않는다.
- Git 제외는 단계에 따라 9절대로 적용한다. 최종 구성에서 `.ai-logging/`, `ai-logs/live/`는 제외하고 `ai-logs/snapshots/`는 추적한다. `ai-logs/` 전체를 `.git/info/exclude`에 등록하지 않는다.
- `.gitattributes`는 **`ai-logs/snapshots/** -text -merge`로 확정**한다. 1단계 live 제출에는 `ai-logs/live/** -text -merge`도 적용한다. `merge=union`, ours/theirs로 원본을 임의 합치거나 선택하지 않는다.
- GitHub PR 병합 등 로컬 master 병합 명령을 거치지 않는 master 반영은 사용하지 않는다. README·AGENTS.md에 명시한다.

### 8.2 단일 feature의 작업·리뷰·보완 흐름

1. 활성 feature가 없는지 확인한 뒤 master에서 새 feature를 만든다. 여러 feature를 동시에 수정하는 운영은 범위에서 제외한다.
2. feature에서 구현·테스트한다. 대화·명령·파일 변경을 hook이 수집한다. 단계 로그 커밋은 턴 종료와 빈 index 조건에서 자동 생성한다.
3. feature를 develop에 일반 merge하고 검토·검증한다. develop에서 기능 수정을 하지 않는다. 수정이 필요하면 결과만 기록한다.
4. 리뷰가 끝나면 리뷰 게시 명령이 전체 최신 로그를 확정하고 **로그 경로만 추가하는 커밋**을 만든다. 기능 검증의 성공뿐 아니라 실패 결과도 게시 대상이다.
5. 게시 명령이 해당 로그 커밋만 master에 cherry-pick하고 master의 비-로그 파일 불변성을 확인한 뒤 develop/master를 push한다. 단계별 동작은 8.7절에 따른다.
6. 보완·추가 작업이 필요하면 현재 feature 작업을 재개하는 자동 흐름이 원격 master를 fetch하고 해당 master를 feature에 일반 merge한다. source 변경은 그 다음에 시작한다. 기존 feature를 삭제·재생성하거나 rebase하지 않는다.
7. 보완 후 같은 feature를 develop에 재병합·재검증하고 로그 게시를 반복한다. 수정은 언제나 feature에서 한다.
8. 기능 검증이 통과하고 추가 작업이 없으면 사용자 master 기능 병합 명령으로 feature를 master에 병합한다. 리뷰 로그 게시만으로 기능 코드가 승인·배포됐다고 간주하지 않는다.

새로운 feature는 앞선 feature의 master 반영·작업 종료 후 생성한다. 보완 작업을 하지 않고 바로 최종 기능 병합할 때는 로그를 받기 위한 불필요한 feature 역병합을 먼저 만들지 않는다.

### 8.3 검증된 feature의 판정

- feature의 첫 번째 부모 이력을 따라 마지막 **비-로그 커밋 C**를 찾는다. 일반 로그 전용 커밋은 `ai-logs/snapshots/` 아래 파일을 **추가만** 하고 검증된 스냅샷을 완전하게 포함하는 단일 부모 커밋이다. 수정·삭제·이름 변경·소스 변경은 비-로그 변경이다. 최신 master를 받아들이는 merge는 첫 번째 부모 대비 변경이 검증된 스냅샷 추가뿐이고 비-로그 트리가 동일한 경우에만 로그 기준 갱신으로 인정한다. 그 밖의 merge는 비-로그 변경이다. 이 예외 merge를 로그 게시용 cherry-pick 대상으로 사용하지는 않는다.
- C가 develop의 조상인지 확인한다. C 뒤부터 feature HEAD까지는 모두 위 정의의 로그 전용 추가 커밋이어야 한다. 단순히 코드 내용이 비슷하거나 오래된 feature 버전이 develop에 들어간 것으로 대체하지 않는다.
- develop에 포함됐다는 사실만으로 테스트 통과를 추정하지 않는다. 검증 실행기가 C, 테스트한 develop HEAD/비-로그 코드 상태, 실행한 검사와 결과를 기록한다. 해당 코드 상태의 실제 통과 기록이 있어야 한다.
- feature 수정 후 develop에 재병합하지 않았거나, develop에서 실패했거나, 테스트 이후 비-로그 코드가 바뀌었다면 검증을 다시 요구한다. 로그 추가나 위 조건을 통과한 master 로그 기준 갱신만으로 이전 기능 검증을 무효화하지 않는다. 그 뒤 실제 보완 코드가 생기면 새 C로 develop 재병합·재검증해야 한다.
- 검증 기록은 로그 전용 커밋의 판정 조건을 깨지 않도록 `.ai-logging/`에 보관하고 원본 세션에도 실제 테스트 명령·결과가 남도록 한다. 누락·모순이면 완료라고 추정하지 않는다.

### 8.4 index와 단계 로그 커밋 검증

- source 작업과 로그 추가의 자동 스테이징을 분리한다. 단계 로그 커밋은 모든 턴 idle·빈 index·예약된 현재 브랜치 조건에서만 만든다.
- 실제 index 파일·manifest·원본을 읽기 전용 검사한다. source 혼합, 비밀 치환 목록, 부분 스냅샷, 기존 스냅샷 수정·삭제, 가변 공통 색인을 거부한다. 일반 feature → develop/master merge는 코드와 기존 스냅샷을 함께 반영할 수 있으나 결과를 검증한다.
- commit-msg는 공통 메시지 형식·스냅샷 원본성을 검사하고 실패하면 비정상 종료한다. sync·파일 수정·자동 스테이징·메시지 수정은 하지 않는다.
- 단계 커밋은 당시 전체 원본을 담지만 이후에 이어진 대화까지 포함한다고 표시하지 않는다. 최종 전체본 확인은 master 병합과 pre-push가 수행한다.

### 8.5 사용자 master 기능 병합 명령: feature 이름을 인수로 받음

명령 이름은 구현 시 확정한다. **사용자가 대상 feature 이름을 인수로 주어 한 번 실행**하며 별도 로그 sync·복사·커밋은 요구하지 않는다. 원래 브랜치·각 HEAD·완료 단계를 `.ai-logging/` 재개 상태에 기록하고 다음 순서를 따른다.

1. **턴 종료 확인:** 모든 등록 세션이 idle인지 확인한다. active/unknown이면 중단한다. 보호 잠금을 확보해 확인 직후 새 턴이 시작되지 않게 하며, 원본 쓰기·hook 마무리 상태도 대조한다.
2. **작업 폴더 확인:** 스테이징·수정·삭제·미추적 파일 및 진행 중 Git 작업이 없는지 확인한다. Git 제외 live와 로컬 상태는 제외한다. 깨끗하지 않으면 중단하고 자동 stash·강제 정리는 하지 않는다.
3. **feature 검증 이력 확인:** 8.3절의 C가 develop에 포함돼 있고 그 뒤는 스냅샷 추가 전용 커밋인지 검사한다. 해당 코드의 develop 검증 통과 기록도 확인한다. 다른 worktree에서 사용 중인 대상 브랜치나 도중에 바뀐 HEAD는 강제 처리하지 않는다.
4. **남은 최종 로그를 feature에 추가:** 리뷰 게시로 master에 이미 반영된 스냅샷과 모든 프로젝트 세션의 최신 원본을 대조한다. 리뷰 게시 뒤에 원본이 더 늘었다면 그 최신 전체 스냅샷을 대상 feature에 로그 전용 커밋으로 추가한다. develop 검증 세션·부속 파일도 빠짐없이 확인한다. 같은 ID는 재사용하며 source 내용은 변경하지 않는다. feature에 없는 기존 master 스냅샷은 이어질 merge가 보존하는지 결과에서 검사한다.
5. **feature → master 병합:** 공통 커밋 형식으로 `--no-ff` 일반 merge한다. develop은 병합 대상이 아니다. source 충돌을 자동 선택해 해결하지 않는다.
6. **병합 결과 읽기 전용 검증:** master 커밋 트리에서 모든 등록 세션의 최신 전체 원본·부속 파일이 있는지, develop 검증 기록까지 포함됐는지, 해시·목록·순서·마스킹 조건을 확인한다. feature의 source만 반영됐는지 별도로 검사한다.
7. **원래 브랜치로 복귀:** 성공 결과와 병합 커밋을 기록하고 원래 브랜치로 돌아간다. 복귀 후 로그 live·등록 상태가 유지되는지 확인한다. 자동 push는 하지 않는다.

- 실패하면 해당 단계에서 멈추고 상태를 남긴다. 안전하지 않은 자동 복귀·rollback·merge abort를 수행하지 않는다. 충돌 해결이 필요한 상태와 재시도 가능한 상태를 구분한다.
- 재실행 시 먼저 턴·HEAD·작업 상태를 다시 확인하고, 자기 실행이 만든 것으로 검증된 스냅샷/index 작업만 이어간다. 외부 변경은 섞지 않는다. 같은 원본·정책은 같은 ID이므로 중복 생성·중복 커밋을 하지 않는다.
- 이미 feature 로그 커밋이나 master 병합이 완료됐다면 실제 Git 이력으로 확인하고 그 뒤 단계부터 재개한다. 후속 원본이 늘어났으면 옛 완료 표시를 신뢰하지 않고 최종 로그 확정부터 다시 수행한다.
- 6단계 실패가 이미 만들어진 merge commit을 없애지는 않는다. 실패 상태를 보고하고 push를 차단한다. 문제를 해결하기 전 최종 제출 완료로 표시하지 않는다.

### 8.6 master pre-push: 읽기 전용 최종 방어

- `.githooks/pre-push`에서 hook 입력의 **원격 대상 ref가 `refs/heads/master`인 항목**을 검사한다. 현재 체크아웃된 브랜치나 로컬 이름만으로 판정하지 않는다.
- 실제 전송할 local object ID의 Git 트리를 읽어 모든 등록 세션의 최신 원본과 부속 파일이 포함됐는지 검증한다. 작업 폴더나 전송하지 않는 최신 local master만 확인하지 않는다.
- 진행 중/unknown 턴, 원본 부재·변경, 최신 로그 누락, develop 검증 기록 누락, 미해결 민감정보·정책 불일치이면 비정상 종료로 push를 거부한다.
- sync·마스킹·스냅샷 생성·스테이징·커밋·브랜치 전환은 하지 않는다. 거부 사유만 값 없이 알린다. 누락 보완은 진행 중인 리뷰 게시 또는 master 기능 병합 명령을 다시 실행하면 자동 처리한다. 기능 검증 실패 기록의 로그 게시도 허용하되, 이 경우 master의 source가 변경되지 않았는지는 게시 명령이 별도로 검증한다.
- 검사는 실행 시점의 완전성을 확인한다. 그 이후 새로운 AI 작업이 생기면 다시 로그가 필요하다. `--no-verify`, hook 비활성화, GitHub PR 등 서버 측 master 병합으로 우회하지 않는 규칙을 README·AGENTS.md에 둔다. 이 로컬 hook이 서버 정책을 대신한다고 주장하지 않는다.

### 8.7 리뷰 게시 명령: develop 로그 전용 커밋만 master에 동기화

사용자가 리뷰 결과를 push하는 동작을 이 명령 하나로 제공한다. 대상 feature를 인수로 받고 기존 작업 스크립트 안의 하위 명령으로 구현한다. 정상 흐름에서 사용자가 커밋 해시를 찾거나 별도 cherry-pick·master push를 수행할 필요는 없다. 일반 `git push develop` 자체가 선택 커밋 전달까지 수행하는 기능은 아니므로 README의 리뷰 게시 진입점을 사용한다.

1. 모든 등록 턴이 idle인지, 작업 폴더와 index가 깨끗한지, 활성 feature가 하나인지, develop 리뷰 대상이 그 feature인지 확인한다. 보호 잠금과 HEAD를 기록한다.
2. 원격 상태를 fetch하고 develop/master의 로컬·원격 관계를 확인한다. 정상적인 fast-forward로 맞출 수 없는 차이·예상하지 못한 source 변경은 강제 처리하지 않는다.
3. develop에서 모든 프로젝트 세션의 최신 원본을 sync·마스킹·검증한다. 새 전체 스냅샷을 추가하고 공통 형식의 **로그 전용 단일 부모 커밋**을 만든다. 같은 스냅샷이면 기존 완료 기록을 재사용한다.
4. 선택한 커밋의 diff가 `ai-logs/snapshots/` 파일 추가만 포함하는지 검사한다. 소스·설정·삭제·기존 스냅샷 수정이 섞이면 master에 적용하지 않는다. 커밋 메시지만으로 로그 전용 여부를 판단하지 않는다. master의 스냅샷 목록과 비교해 이번 게시에 필요한 미반영 로그 전용 커밋도 자동 선택한다. 마지막 리뷰 커밋의 부모에만 있는 기존 로그를 놓치지 않는다. 선택 목록은 Git 이력과 manifest에서 계산하며 사람이 따로 관리하지 않는다.
5. 최신 master에 선택한 로그 전용 커밋들만 순서대로 `cherry-pick -x`한다. source merge commit이나 develop 전체를 선택하지 않는다. 원래 develop 커밋과 master의 새 커밋 SHA는 달라도 스냅샷 내용은 같아야 한다. 이미 반영된 내용은 해시 검증 후 중복 적용하지 않는다. 적용 전후 master의 `ai-logs/snapshots/` 밖 경로·파일 mode가 모두 동일한지 확인한다. 필요한 스냅샷을 source 혼합 커밋에서만 찾을 수 있으면 해당 커밋을 통째로 적용하지 않고 게시를 보류한다.
6. master에 모든 등록 세션의 최신 전체본이 있는지 검사한 후 develop과 master를 원격에 게시한다. 같은 원격에서 `--atomic` push를 사용해 둘 다 반영되거나 둘 다 거부되도록 하는 방식을 우선 검증한다. 서버가 이를 지원하지 않으면 조용히 부분 게시하지 않고 미지원으로 보고한다. `develop:master` push나 force push는 사용하지 않는다.
7. 게시한 양쪽 원격 ref와 로그 포함 여부를 확인하고 원래 작업 브랜치로 돌아간다. 보완 작업의 feature 재개는 8.8절에서 최신 master를 반영한다.

- 기능 테스트 실패도 AI 활용 기록이므로 로그 게시 자체를 막는 이유가 아니다. 반면 개인정보·원본성·턴 상태 검증 실패는 게시를 차단한다.
- 모든 변경은 턴이 종료된 명시적인 게시 작업 안에서만 한다. pre-push에서 master 변경·중첩 push를 수행하지 않는다.
- 네트워크 오류·push 거부·중단 시 로컬 적용과 원격 게시의 완료 상태를 구분한다. 재실행은 실제 커밋·스냅샷·원격 ref를 확인해 이어가며 중복 cherry-pick·불필요한 빈 커밋·자동 reset을 하지 않는다.
- atomic push는 원격 두 ref의 게시를 묶을 뿐, 로컬 커밋이나 브랜치 전환을 되돌리는 기능은 아니다. 로컬 재개 상태는 기존 `.ai-logging/` 작업 상태에 함께 보관한다.
- 이 흐름은 master에 검증된 **로그만 먼저 게시할 수 있는 예외**다. 기능의 master 반영 승인과 혼동하지 않는다. AI가 임의 시점에 master source를 바꾸거나 push하는 권한으로 확대하지 않는다.

### 8.8 보완 작업 재개: 최신 master를 현재 feature에 반영

- 턴이 끝난 작업 재개 단계에서 원격 master를 fetch하고 확인된 master 커밋을 현재 feature에 일반 merge한다. 막연히 현재 브랜치에서 `git pull`만 실행해 다른 upstream을 가져오지 않는다.
- 리뷰 게시 이후 master에 추가된 것이 로그뿐인지 확인한다. 예상 밖 source 변경·dirty index·활성 턴·충돌은 자동 덮어쓰기하지 않는다.
- 로그 ID·파일 해시로 누락·중복을 확인하고 최신 리뷰 로그가 feature에 존재하는지 검사한 뒤 source 보완 작업을 시작한다. source가 아직 미검증이어도 로그 동기화로 master에 역유입되지 않는다.
- 여러 feature에 전달하는 순회는 없다. 하나의 활성 feature만 최신 master를 받는다. 기능 수정 후에는 develop 재병합·재검증을 다시 수행한다.

## 9. 구현 순서: 세 단계와 통과 기준

각 단계의 코드·설정·실제 동작을 검증한 뒤 다음 단계로 간다. 현재는 계획만 작성하며 테스트 파일·임시 Git 저장소도 만들지 않는다.

### ① 등록·live·마스킹·검증·README: 최소 제출 요건 확보

- 두 도구 원본 탐색·등록·소급 수집, SessionStart/Stop 및 Claude SessionEnd 수집, 기본 치환 목록 설치 시 확정, 전체 원본성·민감정보 검사, 상태 확인, README·공통 규칙을 구현한다.
- **1단계 단독 제출에서는 `ai-logs/live/`를 Git 제외하지 않는다.** 검증된 전체 원본과 부속 파일, manifest, README, 설정·스크립트를 일반 프로젝트 제출물에 포함할 수 있게 한다. 로그를 따로 선별·복사하는 수동 절차는 두지 않는다.
- 첫 전체 수집이 최초 요청·수정 요청·Claude 계획 검증·이후 세션을 모두 포함해야 한다. 원본의 계속되는 추가와 마지막 응답 뒤 꼬리를 다시 수집할 수 있어야 한다.
- 완료 기준: 실제 두 도구의 수집을 확인하고 민감정보·바이트 대조를 통과하며, **제출 Git 트리에 전체 원본 사본과 README·설정·스크립트가 포함되는 것까지 확인**한다. Git 제외 live만 존재하면 최소 제출 요건 완료가 아니다.
- 1단계만 사용할 경우 중간 브랜치 자동 운영·단계 커밋은 제공하지 않으며, 모든 AI 작업 종료 후 일반 프로젝트 제출 절차에서 결과를 포함한다. ②·③ 기능이 없어도 평가에 필요한 도구·설정·전체 트랜스크립트 산출물은 완비한다. 아직 구현하지 않은 자동 Git 보호까지 갖췄다고 표시하지 않는다.

### ② 단계 스냅샷·로그 커밋·턴 상태 보호

- UserPromptSubmit/Stop 상태, active/unknown 보호, 공통 잠금, 빈 index 보호, 단계 예약, 결정적 스냅샷·로그 전용 커밋, commit-msg 검증을 구현한다.
- 같은 브랜치에서 단계 로그를 확정하며 다른 feature로 순회·전달하지 않는다.
- **스냅샷에 ① live의 모든 세션·부속 파일을 보존했음을 먼저 검증한 뒤** live를 Git 제외로 전환한다. 이미 추적됐다면 스냅샷 추가와 live 추적 해제를 하나의 명시적인 구성 이행으로 검토한다. 실제 live·원본 파일은 삭제하지 않는다. 이 구성 이행은 일반 단계 로그 추가 커밋으로 위장하지 않는다.
- 완료 기준: 두 도구 턴 경합·이전 Stop 지연·unknown·staged source 보호·같은 길이 다른 hash·50MB 경고·원본성·중단 재개를 통과한다. 첫 스냅샷 커밋 전에 기본 치환 목록과 전체 검증이 통과해야 한다.

### ③ 리뷰 로그 게시·보완 재개·master 기능 병합·pre-push

- feature 이름을 인수로 받는 리뷰 게시·보완 작업 재개·8.5절의 master 기능 병합을 기존 작업 스크립트에 구현한다. 검증 코드 판정·테스트 결과 연결·재실행 상태·읽기 전용 pre-push를 공유한다. 별도 상주 서비스나 다중 feature 동기화 관리자는 만들지 않는다.
- README·AGENTS.md에 리뷰 게시 명령, 로그만 master에 먼저 반영하는 예외, master를 받아 feature 보완을 이어가는 방식, 최종 feature → master 기능 병합, 로컬 명령 외 master 반영 금지, 프로젝트 전체 대화 포함 원칙을 적는다.
- 완료 기준: 10절의 실제 Git 브랜치 시나리오와 두 도구 실제 hook 검증을 통과하고 원본·Git 트리 비교 결과를 남긴다. fixture만 통과한 것을 실제 세션 검증 완료로 표시하지 않는다.

## 10. 최종 검증: 브랜치 전략으로 로그가 유지되는지

### 10.1 단일 feature의 리뷰 게시·보완·재병합 시나리오

1. master에서 feature A를 하나 만들고 Codex·Claude 대화, 명령, 파일 변경·실패를 기록한다. 다른 활성 feature가 있으면 신규 작업 흐름이 거부되는지 확인한다.
2. A를 develop에 병합하고 develop에서만 검증 세션·subagent/tool-results를 생성한다. 기능 실패를 기록하되 source 보완은 develop에서 하지 않는다.
3. 리뷰 게시 명령을 실행한다. develop의 새 로그 전용 커밋만 master에 반영·push되며 **master의 비-로그 파일은 게시 전과 동일하고 A의 미검증 source는 master에 없어야 한다.** 실패 기록·부속 파일은 포함되어야 한다.
4. feature 보완 재개 흐름으로 최신 master를 A에 병합한다. master 리뷰 로그가 A에 이어지고 기존 대화·source 변경이 보존되는지 확인한다.
5. A에서 수정한 뒤 develop에 아직 재병합하지 않았거나 테스트가 실패한 동안은 master 기능 병합이 거부되는지 확인한다. 이때 실패 로그를 master에 게시하는 것은 source 무변경 조건에서 가능해야 한다.
6. 수정한 A를 develop에 재병합·재검증하고 로그를 다시 게시한다. 같은 커밋을 재시도해도 중복 스냅샷·중복 cherry-pick이 생기지 않아야 한다.
7. 기능 검증 통과 뒤 사용자 master 기능 병합 명령으로 A를 일반 merge한다. A의 수정 코드와 최초 요청부터 develop 실패·재검증까지 전체 로그가 master에 있어야 한다.
8. 종료 후 다음 feature B를 master에서 만든다. 이전 A 대화와 develop 검증 이력을 그대로 이어받고 B의 새 로그가 누적되는지 확인한다. A·B를 동시에 수정하지 않는다.
9. merge/push 이후 원본에 새 대화가 생겼다면 pre-push가 오래된 로그를 거부해야 한다. 해당 게시·최종 병합 명령의 재실행으로 자동 보완되는지 확인한다.

추가 실패 조건 테스트로, 선택한 로그 커밋에 source 변경을 섞었을 때 게시가 거부되는지 검사한다. Git 충돌이 없다는 사실만으로 source 격리 성공을 판정하지 않는다.

최초 게시에서 마지막 리뷰 커밋보다 앞선 로그 커밋에만 있는 세션도 master에 반영되는지 검사한다. 이미 게시된 로그를 feature가 master merge로 받은 뒤에는 중복 커밋 없이 source 검증 상태가 유지되는지도 확인한다.

### 10.2 develop ai-logs의 master 반영 전용 검사

- develop 원본 세션과 develop 커밋의 manifest에서 세션 ID·원본 길이·원본/사본 해시·부속 파일 목록을 추출해 최종 master의 최신 전체본과 대조한다.
- 리뷰 게시 대상으로 선택한 로그 커밋의 스냅샷 경로·manifest·파일 바이트가 master에 동일하게 들어가는지 검사한다. cherry-pick으로 commit SHA가 달라지는 것은 정상이다. 별도로 **모든 develop 원본 내용이 master의 최신 전체본에 보존됐는지** 확인한다. 선택하지 않은 과거 중간 커밋의 SHA까지 master에 존재할 필요는 없다.
- 동일 세션에서 develop 이후 feature 대화가 더 붙었으면 develop 시점의 원본이 최종 원본의 동일한 앞부분인지 확인한다. 최종 사본은 적용 정책으로 전체 원본과 대조한다. 마스킹 전후 길이가 같다고 가정하지 않는다.
- develop에서만 생성된 세션·subagent·tool-results, 타임스탬프 없는 줄, 실패·중단·재검증 기록을 각각 확인한다. 하나라도 누락하면 master 병합 결과 검증과 pre-push가 실패해야 한다.
- 최종 master에 세션별 최신 전체본이 존재하는지와, 이미 커밋한 과거 스냅샷을 불필요하게 수정·삭제하지 않았는지를 별도로 확인한다.

### 10.3 실패·경합·정책 변경 검사

- 어느 한 세션이 active/unknown인 경우 source Git 변경·단계 로그 커밋·master 병합·master push 보류/거부.
- UserPromptSubmit과 Git 보호 잠금의 동시 접근, 과거 Stop이 새 턴을 해제하는 문제, hook 시간 초과·비정상 종료 후 상태 유지.
- shared index의 staged source, dirty 작업 폴더, 외부 HEAD 변경, 다른 worktree에서 사용 중인 대상 브랜치 보호.
- feature 미검증 코드·develop 미포함·검증 실패·통과 뒤 code 변경·로그 경로 수정/삭제를 추가 전용으로 오판하지 않는지.
- 원본 앞부분 불일치·절단·부속 파일 누락·사본 변조·JSON 이스케이프 민감값 잔류·허용 목록·구조 필드 예외·오탐 사례.
- `L` 0채움 정렬, 동일 내용 재사용, 동일 길이 다른 hash 보류, 정책별 구분, 50MB 경고, Git blob 개행 불변성.
- 로그 커밋·master cherry-pick·remote push·기능 merge·검증·브랜치 복귀 단계별 실패와 멱등 재실행. source 혼합 커밋 거부, master 비-로그 파일 불변성, 같은 스냅샷 재적용, atomic push 지원·거부·네트워크 오류를 검증한다. 자동 이력 재작성은 없다.
- master refspec의 실제 전송 OID 검사, 다른 브랜치에서 master로 push하는 경우, 더 오래된 커밋 전송, merge 후 추가 대화에 대한 pre-push 거부.
- ① 단독 제출, ①→② 이행, 이후 정책·폴더 구조 변경에도 최초 요청부터의 원본이 유지되는지.

검증 결과에는 실행한 검사, 확인한 commit·세션·파일 수·해시, 통과/실패와 미확인 항목을 기록한다. 로그에 실제 비밀값을 출력하지 않는다. 자동 처리가 확인되지 않으면 수동 로그 운영으로 대체하고 완료라고 하지 않는다.

### 현재 상태와 구현 결정 (2026-11-04, Claude Code 구현 반영)

①②③ 단계를 모두 `feature/LOG-001`에 구현했다. 실행·검증 결과와 미확인 항목은 README "검증 기록"이 기준이다.

사용자 결정으로 계획과 달라진 점

- develop 로그는 사용자가 develop을 push할 때(`push-develop`)만 master에 동기화한다. develop 기능 검증은 자동화하지 않는다.
- 스냅샷 폴더 이름에는 sha256 앞 16자만 쓴다(`L<20자리>-<16자>`). 전체 해시는 manifest `snapshot_sha256`에 기록한다.
- 이번 작업에서는 실제 develop 병합·검증을 하지 않는다. 흐름 명령은 임시 저장소와 로컬 bare 원격으로 검증했다.
- `feature/LOG-001`의 로컬 커밋은 squash로 합쳐 둔다: 소스 커밋 1개 + 로그 전용 커밋 1개.

구현 방식의 결정

- **cherry-pick**
  - develop 로그 전용 커밋의 master 반영은 `cherry-pick -x`와 같은 결과로 만든다(원 작성자·메시지, `(cherry picked from commit …)`).
  - 작업 폴더 전환 없이 `git merge-tree --merge-base` + `commit-tree` + 비교 후 교체로 처리한다. 충돌하면 아무 ref도 바꾸지 않고 멈춘다.
- **최종 병합**
  - `merge-feature`의 `--no-ff` 병합도 `merge-tree --write-tree`로 두 부모 커밋을 만들어 로컬 master ref만 옮긴다(push 없음).
  - `resume`은 feature를 체크아웃한 경우 일반 `git merge --no-ff`를 쓴다(commit-msg hook 실행).
- **Claude 턴 종료 판정**
  - Claude hook 입력에는 turn_id가 없다. 그래서 Stop의 `last_assistant_message`가 이 턴 시작 offset 이후 원본에 있는지로 판정한다.
  - 원본 기록이 늦을 수 있어 최대 10초 다시 읽는다.
  - 확인하지 못하면 상태를 바꾸지 않는다. 이후 원본의 `turn_duration` 증거로 idle이 된다.
- **정책 버전**: 허용 목록 파일 바이트가 아니라 정규화한 JSON 내용으로 계산한다(core.autocrlf 체크아웃으로 개행만 바뀌어도 정책이 바뀌던 문제 수정).
- **Git hook 런타임**: hook과 수집기 사본을 `.git/ai-logging/runtime/`에 둔다. 로깅 설정이 없는 master로 전환해도 hook이 유지된다.
- **최초 도입 예외(LOG-001)**: master에 설정이 없을 때는 `new-feature`·`push-develop`을 거부하고, `merge-feature feature/LOG-001`만 허용한다.
