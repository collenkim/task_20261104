이번 응답 계약 수정에는 인덱스·쿼리·캐시·커넥션 풀 변경이 필요하지 않았다. p50/p95·처리량·CPU·메모리·대규모 데이터 분포를 측정하지 않았으며 성능 향상을 주장하지 않는다. 사용자의 DB에 성능용 데이터를 넣거나 초기화하지 않았다.

P-06의 무제한 원격 본문 읽기는 예외로 보완했다. 멤버 업무 조회는 1MiB, Swagger API 중계는 1MiB, 명세 중계는 2MiB로 제한한다. `readNBytes(상한 + 1)`로 초과 여부를 확인하고 스트림을 닫는다. 상한 안의 JSON 파싱과 객체 생성 메모리까지 해당 바이트 수 이하라는 뜻은 아니다. local 클래스패스 fixture의 읽기는 네트워크 입력과 구별해 유지한다.

업무 조회의 기존 계약 오류 상태는 유지하고, 기술 중계는 502 GROUP_RESPONSE_TOO_LARGE로 구분한다. 업무 1MiB 정확한 경계·초과 거부, API 중계 초과, 명세 2MiB 초과는 합성 HTTP 응답으로 검증한다. 재시도 후에도 응답 본문 제한 시간이 적용되는지 확인한다. 별도 타이머 스레드를 추가하지 않고 기존 JDK 전송기의 읽기 제한을 사용한다.

P-01·02·03·07의 count·정렬·offset·집계, P-04·13의 원격 대기와 풀, P-05·08·11의 전송·IN padding·명세 캐시, P-09의 정규식 최적화는 측정 근거 없이 변경하지 않았다. P-10의 INFO/ERROR 추적과 P-12의 REPEATABLE_READ·조회 일관성도 보존했다. 회로 차단·동시 호출 제한은 별도 승인 전 현행 유지다.

향후 성능 개선은 별도 Compose/DB에서 대표 데이터 분포와 정상·지연·중단 시나리오를 고정한 뒤 전후 수치를 수집해야 한다. 이번 실제 Compose와 Swagger 검사는 기능 적합성의 증거이며 부하 시험으로 해석하지 않는다.

## 2차 변경 (2026-11-06)

2차 승인으로 요청 경로에 단계가 추가되었다. 아래는 코드 검토로 확인한 비용과 병목 후보이며 측정값이 아니다.

| 구간 | 추가된 일 | 병목 후보와 한계 |
| --- | --- | --- |
| JWT 검증 | `/api/**`·중계 요청마다 RS256 서명 검증과 iss·aud·exp·nbf·sub·scope 확인 | 공개키는 시작 때 한 번 읽는다. 원격 JWKS 조회·캐시는 없다. 서명 검증은 요청마다 CPU를 쓴다 |
| 요청 제한 | subject별 토큰 버킷(`ConcurrentHashMap`, 버킷 단위 동기화) | 단일 인스턴스 메모리 상태라 여러 인스턴스 간 공유되지 않는다. 추적 수가 상한(10,000)이면 새 subject마다 전체 버킷을 훑어 가득 찬 버킷을 지운다. 모두 활성 상태면 지울 수 없어 상한을 넘을 수 있다 |
| GET 전용 필터 | 모든 요청 앞의 메서드 비교 | 조회·인증보다 먼저 405를 돌려 HEAD·OPTIONS가 DB·그룹을 호출하지 않는다 |
| summary 중복 제거 | 입력 순서 유지 중복 제거, 중복이 있을 때만 WARN 1줄 | 입력 상한 100이라 비용은 작다. 중복 ID 원문을 남기므로 로그 양은 중복 요청 수에 비례한다 |
| local 토큰 발급 | Swagger 초기화 스크립트 요청마다 RSA 서명 | local 프로필 전용이며 공개 경로라 요청 제한을 받지 않는다. 기본 프로필에는 발급 경로가 없다 |

오류 코드 변경에 따라 크기 초과는 502 `BAD_GATEWAY` + type `urn:problem-type:group-response-too-large`로 바뀌었다. 위 기록의 `GROUP_RESPONSE_TOO_LARGE`는 1차 당시 코드다.
