- 승인 후 준비 검사에서 29개 정확한 값은 모두 허용되고, 앞뒤에 미검토 문자를 붙인 58개 변형은 모두 거부되었다. 마스킹할 두 후보는 허용 목록에 포함되지 않았다.

## 최종 제출 절차와 남은 범위

이 문서 작성 시점에는 새 소스·설정이 아직 커밋되지 않았다. 네 세션의 새 스냅샷은 생성됐지만 원격 master 제출 완료를 뜻하지 않는다. 현재 대화는 계속 추가되므로 모든 턴 종료 후 다시 수집해야 한다.

로컬 `.ai-logging/log-finalization/finish-submission.py --apply`를 사용자 터미널에서 실행하도록 준비했다. 실행은 모든 세션 idle, 예약 작업 완료, 검토한 파일 해시·브랜치·index 상태가 일치할 때만 시작한다. Git hook 런타임을 갱신하고, develop에서 준비된 변경을 동일한 소스 기준의 feature로 가져가 커밋한 뒤 `resume`으로 최신 master를 반영한다. 이어 develop에 병합해 Python 전체 검사와 문서 검사를 실행하고, 마지막 응답까지 재수집·완전성 검증 후 `merge-feature`로 master에 반영한다.

새 허용 목록을 포함한 master를 먼저 push한 뒤 `push-develop`으로 develop 로그를 동기화한다. 이는 이전 master 정책으로 새 로그를 검사하는 불일치를 피하기 위한 순서다. master에 develop 전체를 병합하지 않는다. 마지막으로 실제 원격 SHA 일치·완전성·커밋 비밀값·develop 로그의 master 포함을 검사하고 로컬 `submission-receipt.json`에 결과를 기록한다. 실패하면 멈추며 자동 stash·reset·force push·원본 편집은 하지 않는다.

이 턴의 단계 로그는 수집기 `stage-log` 예약 `c61722f290a0`으로 종료 후 커밋하도록 요청했다(`pending`). 예약 성공과 실제 실행 완료는 `task list`에서 구분해야 한다. 소스 커밋·master 반영·push·원격 제출 검증은 위 사용자 실행이 성공해야 완료다. 기준은 [AGENTS.md](../../../AGENTS.md)의 턴 중 Git 변경 금지와 사용자 master 제출 절차다.

## Stop hook 중단 후 제출 재개 보완

사용자가 위 제출 명령을 실행했으나 `reserved_tasks_not_finished`로 시작 전 중단됐다. 2026-11-06 후속 진단에서 다음을 확인했다.

- Codex Stop 제한은 120초였으며, Stop 등록은 `04:02:40.402Z`, live 수집 저장 완료는 약 `04:03:22Z`였다. 이후 `04:03:23.498Z`의 스냅샷 수집 잠금이 남았고 소유 프로세스는 종료돼 있었다. 수집기 자체 오류 기록은 없었다. 사용자 hook 실패 보고와 이 상태는 외부 시간 초과에 부합하지만, 원본에서 정확한 timeout 종료 이벤트는 확보하지 못했다.
- 예약 `c61722f290a0`은 `failed`가 아닌 `pending`이었고 develop HEAD는 여전히 `fcc5210`이었다. 커밋 전에 멈춘 상태다. 읽기 전용 검사에서 스냅샷 manifest 18개와 해당 사본의 누락·해시 불일치는 모두 0이었다.
- 제출 스크립트가 `pending`도 무조건 거부해 복구 경로가 없었다. 이를 수정해 검토한 파일·브랜치를 먼저 확인하고, 같은 턴 보호 잠금 안에서 승인된 해당 단계 로그 예약만 이어 실행한다. 관련 없는 예약·실패한 예약·active/unknown 턴은 차단한다. 잠금을 강제로 지우거나 턴을 임의로 idle로 바꾸지 않는다.
- `.codex/hooks.json`의 SessionStart·Stop을 120초에서 600초로 늘렸다. UserPromptSubmit 30초·SessionEnd 3초는 유지했다. 수정한 hook은 Codex 신뢰 재검토가 필요하며, 제출 명령은 hook 신뢰 우회 없이 일반 터미널에서 수집·예약 처리를 수행한다.
- 제출 명령의 잠금 대기·예약 복구·주요 검증·push 단계는 15초마다 경과 시간을 표시한다. hook의 120초 실행 제한에 의존하지 않는다. 검토 대상 파일 해시 목록도 변경 사항에 맞게 다시 생성한다.

검증은 임시 저장소에서 수행했다. 중단 뒤 기존 스냅샷 재사용·추가 턴 진행 시 차단 회귀를 저장소 테스트에 추가했고, `test_guard_snapshots.py`의 36개 검사가 모두 통과했다(108.435초, 종료 코드 0). 로컬 제출 스크립트의 예약 재개·중복 커밋 방지·진행 중 턴 차단·미승인 예약 거부·실패 예약 유지 검사는 4개 모두 통과했다(11.860초, 종료 코드 0). 실제 저장소의 읽기 전용 `--check`도 검토 파일 14개·재개 대상 예약 1개를 확인했다. 실제 저장소의 Git 변경과 원격 제출은 이 대화가 끝난 뒤 같은 `finish-submission.py --apply` 명령으로 실행해야 한다.
