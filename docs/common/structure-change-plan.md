> SETUP-001 당시 구조 변경 계획이다. 현재 그룹 Swagger 실행은 [GROUP-001 요청서](requests/GROUP-001.md)의 멤버 중계 규칙이 대체한다.

| 명세 | 멤버 Swagger에서 두 명세를 제공한다. 그룹 명세는 멤버가 받아 전달하며 읽기 전용이다 |
| 상태 | 2026-11-04 G-01~G-14 구현·로컬 검증 완료. 실제 결과는 [재검증 기록](setup-verification.md)에 기록한다 |

## 1. 범위

멤버가 공개 진입점이며 그룹은 내부 IP:PORT로 호출한다. 그룹의 Compose 호스트 앱 포트는 없다. 각 서비스는 자기 DB·스키마·계정·볼륨·네트워크를 소유한다. 업무 엔티티·조회 API는 후속 기능 범위다.

## 3. 완료 기준

1. 멤버 API는 사용자 토큰 없이 호출한다.
2. 정상 키의 그룹 명세는 200, 누락·불일치·중복 키는 403이다.
3. 두 명세를 멤버 Swagger에서 조회한다. 그룹 실행 버튼은 없고 멤버는 실행 가능하다.
4. 브라우저에 키를 주지 않고 그룹에 직접 요청하지 않는다. 전달 경로는 멤버 공개 명세에 없다.
5. 정상 그룹 컨테이너의 8082는 호스트에 공개하지 않는다.
6. 앱 통신 네트워크에는 두 앱만, 각 DB 네트워크에는 자기 앱과 DB만 연결한다.
7. 그룹 중단 중 멤버 기동·readiness·자기 명세는 성공하고 그룹 명세 요청만 503이다.
8. 양쪽 단독 기동이 가능하다. 다른 서비스에 depends_on을 두지 않는다.
9. 포맷·실제 MariaDB JPA·오류·페이지네이션·통신 테스트를 통과한다.
10. 업무 API 미구현과 실제 검증 환경을 기록한다. 로컬 검증으로 develop/master 검증을 대신하지 않는다.

## 4. 구현 순서

계약 → 키 생성·그룹 필터 → 멤버 클라이언트·명세·오류 처리 → Swagger → Compose → 검증 → 문서 현황.

명세 조회와 업무 API 중계는 별도다. 이번에는 명세 조회만 제공하고 필요한 사용자 조회는 후속 멤버 업무 API가 소유한다.
