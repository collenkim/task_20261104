## 1. 시작 조건과 범위

REVIEW-001의 문서 결과가 master와 origin/master에 반영된 뒤 시작한다. 새 브랜치는 그 master에서 만든다. develop 또는 feature/REVIEW-001을 기준으로 만들지 않는다. 동시에 진행하는 feature는 하나다.

착수 기록에는 master SHA, REVIEW-001 병합 SHA, 인계 문서 버전, 네 API의 목표 계약 버전, 선택 정책의 승인/유지/보류 상태, 테스트 기준 수, AI 로그 상태를 적는다. 파일이 있다는 이유만으로 미결정 정책을 승인된 것으로 취급하지 않는다.

README의 최소 설치 조건(R-26)과 실제 환경도 대조한다. JDK 21, Wrapper, Docker CLI/Engine/Compose와 API 접근, Python·Git, 브라우저 자동 검증에 필요한 별도 도구를 확인한다. 최초 generateLocalSecrets 실행에 호스트 JDK가 필요하다는 점을 유지한다. 기능 하한 버전과 실제 검증한 조합을 구분하며 모든 하위 버전 호환성을 검증했다고 표시하지 않는다.

필수 작업은 정의 외 응답 필드 차단, 확정 응답 형태 반영, 부족한 계약·실패·경계 검사, 소유 문서와 생성 OpenAPI 정합이다. JWT·DNS·중복 제거·로그 수준 변경·회로 차단·캐시는 선행 결정에서 승인된 경우에만 구현한다. 비승인 항목은 현행 동작을 유지한다.

코드·테스트와 함께 실제 적용된 문서·예제·검증 기록을 갱신한다. 승인된 계획과 다른 설계가 필요하면 먼저 변경 이유와 계약 영향을 문서화한다. 기존 코드를 통과시키기 위해 기대 응답이나 테스트 기준을 바꾸지 않는다.

## 3. API 응답과 입력 구현

### 3.1 출력 계약

서비스별 api-review.md의 승인 필드 표가 구현 기준이다. 목록 봉투, 각 목록 항목, page, 그룹 객체·배열, 상세, 오류를 각각 검사한다. 최상위 검사만 통과하고 중첩 객체에서 필드가 새는 상태를 허용하지 않는다.

- 멤버 목록·상세는 명시적 Response DTO로 반환한다. Entity·내부 View·원격 JSON을 그대로 공개하지 않는다.
- groups 배열을 group 단일 객체로 변경하거나 createdAt·createdBy를 제외하는 것은 D2·D3 승인 내용에 맞춘다. 제외된 감사 값은 DB에 보존할 수 있으며 응답에서만 제거한다. joinedAt과 registeredDate의 명칭·의미도 승인 표를 따른다.
- 멤버 등록일과 그룹 가입일을 혼용하지 않는다. 저장은 UTC TIMESTAMP(6), 출력은 Asia/Seoul yyyy-MM-dd HH:mm을 유지한다.
- 그룹 상세는 memberId, groupId, groupName, registeredDate, pricing, permission의 기존 6필드 평면 단일 객체다. 다건을 배열이나 대표 행으로 반환하지 않는다.
- code만 외부에 반환한다. enum 내부 status·codeName·description을 삭제하거나 외부 DTO에 함께 넣지 않는다.
- 공개 응답 스키마는 정의 외 속성을 거부하고 실제 직렬화 키 집합을 검증한다. 기존 futureField 허용 테스트는 출력 계약에 맞춰 수정한다.
- 내부 소비자의 새 코드·무시 가능한 추가 필드 허용과 공개 응답의 제한을 구분한다. 소비자가 읽은 원격 추가 필드는 공개 DTO나 중계로 자동 전달하지 않는다.
- 그룹 중계 성공 응답도 승인된 계약대로 검증한다. 미정의 필드·잘못된 타입·필수 필드 누락을 주입한 응답이 외부에 노출되지 않아야 한다. 차단 시 오류 형태는 D15의 결정대로 고정한다.
- 기존 중계의 오류 상태·표준 ProblemDetail 보존, 원문 비노출, 고정 GET 경로, 응답 크기 상한, no-store를 유지한다.
- 계약 변경은 소비자 영향과 버전을 기록한다. 승인된 문서를 현행 api.md로 반영하고 기존 생성 절차로 OpenAPI를 갱신한다. JSON만 수작업 변경하지 않는다.

### 3.2 입력·조회·실패

- 기존 spring.data.web.pageable 블록과 page 응답의 size/number/totalElements/totalPages를 유지한다.
- page/size의 공백·빈 값·음수·정수 범위 초과, 반복 page/size/sort, offset 범위를 검사한다. 이름 오름/내림 정렬과 ID 보조 정렬을 유지한다. 승인 없이 크기 보정·허용 범위를 바꾸지 않는다.
- summary ID 중복 제거가 승인되면 중복 제거 전 원래 입력 수 1~100을 검사한다. 잘못된 ID가 중복 제거로 숨겨지지 않게 하고, 그룹 응답과 totalMemberCount의 의미는 유지한다.
- 멤버 목록의 비어 있지 않은 한 페이지당 논리 summary 호출은 한 번이다. 빈 페이지에서는 그룹을 호출하지 않는다. 재시도에 의한 실제 전송 횟수와 구분한다.
- 상세는 멤버 존재 확인 후 그룹 detail을 호출한다. 미소속 전용 404와 경로 오류·일반 오류를 구분하고, 장애를 미소속 null이나 빈 배열로 바꾸지 않는다.
- 현재 DB UNIQUE(member_id), 동시 중복 입력 차단, 조회 시 다건 예외·ERROR를 유지한다. 응답 형태 정리만을 위해 스키마를 바꾸지 않는다.
- 그룹 5xx·통신 실패에 대한 멤버 503, 계약 오류의 500 등은 승인된 오류 표를 따른다. 원본 group 테스트용 중계와 멤버 업무 API의 상태 변환을 혼동하지 않는다.

## 4. 인증·Swagger — 2026-11-06 승인, 적용

적용 결과: D4·D5·D6 확정에 따라 아래 항목을 구현했다. 멤버 `infrastructure/security/`(Resource Server·검증기·401/403 ProblemDetail·local 토큰 발급), `infrastructure/web/`(GET 전용·요청 제한 필터), Swagger 초기화 스크립트 자동 인증, `task.group-proxy.enabled`로 중계 local 한정, `LocalSecretsTask` 키 쌍 생성. 테스트는 `TestJwt`로 실행 중 키·토큰을 만든다.

JWT를 도입한다면 Resource Server 검증과 local 개발 토큰 발급을 분리한다. 운영 검증에는 공개키를 사용하고, local 발급용 개인키는 운영 기본 프로필의 필수 의존으로 만들지 않는다. 외부 발급 서버를 새로 구축하는 작업으로 확대하지 않는다.

- 검증: 지정 알고리즘·서명·iss·aud·필수 claim·exp·nbf·clock skew·scope. 누락·빈 값·잘못된 타입도 검사한다.
- 경로별 허용표: 멤버 업무 API, 그룹 중계, 그룹 명세 전달, Swagger 자원, health, 오류 디스패치를 나눈다. 예상하지 않은 경로가 자동 무인증으로 열리지 않게 한다.
- 실패 응답: 401·403을 기존 ProblemDetail 및 정의된 필드로 통일하고 보안 필터의 예외 응답도 테스트한다.
- 그룹 중계: local 제한 여부와 별도 권한을 결정표대로 적용한다. Swagger 화면에서 숨기는 것만으로 접근을 막았다고 판단하지 않는다.
- 브라우저 토큰: 수동 Authorize 또는 승인된 local 전용 전달 방식 중 하나를 구현한다. 자동 주입을 선택했다면 토큰이 브라우저에 전달된다는 사실, 유효기간·갱신·캐시 정책을 명시한다. 무인증 공개 자원에 토큰을 넣고 보호가 완료됐다고 하지 않는다.
- 단위·통합 테스트: 실행 중 테스트 키 쌍과 토큰을 생성한다. 실제 실행 검증은 secrets 파일 경로로 읽고, 유효기간 종료 시 재발급 절차를 따른다. 토큰·개인키·내부 키를 소스·출력·AI 로그에 남기지 않는다.
- 멤버 사용자 JWT를 그룹으로 넘기지 않는다. 그룹의 호출자 ID·내부 키 검사는 유지하며 브라우저는 내부 키를 받지 않는다.

## 5. 낮은 결합도와 테스트 정리

- QueryHandler는 입력·출력 포트와 내부 모델을 사용한다. HTTP·JSON·JPA·공개 Response를 application에 끌어들이지 않는다.
- fixture와 실제 HTTP 형식이 다르다는 이유만으로 통합하지 않는다. fixture 해석과 HTTP 계약 해석의 책임을 분리하는 대안을 우선 검토한다. 같은 포트로 동일 업무 결과가 나오는지 검증한다.
- 그룹의 enum·Entity·DTO를 멤버에서 직접 참조하지 않는다. 계약 공유는 OpenAPI 산출물을 사용한다. 다른 서비스 소스 트리 없이는 멤버 테스트를 실행할 수 없는 의존을 만들지 않는다.
- Controller가 infrastructure.configuration에 있어 presentation 규칙을 피하는 부분은 기술 중계의 경계에 맞는 패키지·검사 범위를 정한다. infrastructure와 presentation 사이 모든 참조를 무조건 금지하는 대신 실제 의존 방향을 명시한다.
- 현재 transaction 경계 검사를 유지한다. 실제 저장소 프록시 내부에서는 읽기 트랜잭션, 반환 후 원격 호출·대기에서는 호출 스레드의 트랜잭션이 없어야 한다.
- enum의 필수 메타데이터·페이지 설정·필수 로그 지점을 미사용 코드라는 이유로 삭제하지 않는다. 중복 방어는 계층별 책임을 확인한 뒤 줄인다.

테스트 패키지는 presentation/query·presentation/error·application/query·domain·infrastructure/persistence·infrastructure/client·infrastructure/configuration·architecture·contract·support로 나눈다. 테스트 이동 전후에는 개수뿐 아니라 발견된 테스트 목록, 태그·필터, fixture·리소스 경로, 계약 생성 태스크 포함 여부를 비교한다. 의도적 계층 위반 fixture가 운영 클래스에 섞이지 않게 한다.

| 인증·추적 | 승인된 JWT 실패·scope·프로필, 내부 키 비노출, 잘못된 X-Request-Id 재생성, MDC 정리, 비식별 로그 |
| 계약 검사 | 공식 스키마 유효성·추가 속성 거부·정확한 필드의 독립 기대값·API 예제·소비자 계약·실제 응답 |

상세 500·503 등 기존 테스트가 있는 항목은 재사용하고 부족한 엔드포인트·조건만 추가한다. 실제 실행 결과를 그대로 복사한 기대값만으로 계약을 검증하지 않는다.

## 6. 문서 검사와 동기화

### 추가 요청: clone 직후 비밀 파일 없는 환경

2026-11-05 사용자 추가 요청으로 최초 실행 경로를 검증한다. `secrets/`는 Git에 포함하지 않는다. 현재 Compose는 비밀 파일을 자동 생성하지 않으므로 생성과 기동을 묶는 루트 `startLocal` 태스크를 제공한다. 기존 `generateLocalSecrets`를 재사용하고 기존 키·DB 비밀번호는 유지한다. 생성 실패 시 Compose 기동을 진행하지 않는다.

새 소스 사본에 비밀 파일이 없는 상태로 시작하여 생성·기동·readiness·멤버 경유 그룹 요청을 확인한다. 재실행 시 파일 존재·크기·수정 시각으로 보존을 검사하고 값은 출력하지 않는다. 검증용 Compose 프로젝트·포트·네트워크·볼륨을 격리한다. 기존 DB 볼륨만 남고 비밀번호를 잃은 경우는 최초 설치와 구분하며 자동 초기화하지 않는다. README의 최소 설치 조건과 실제 명령도 함께 맞춘다.

scripts/verification/docs-check.py는 이 브랜치에서 구현한다. 파일·앵커 링크, 정책 정의와 참조, 문서 분류·상태, 현재/적용 예정/이력의 정합을 검사한다. 과거 기록과 금지 동작 설명의 문자열을 정상 계약 위반으로 오탐하지 않도록 범위를 둔다. 계층·요구·테스트 표와도 연결한다.

REVIEW-001 인계표의 비문서 주석 경로를 갱신한다. OpenAPI의 원천은 운영 코드 애너테이션이며 update 태스크로만 공유 JSON을 갱신한다. 일반 build/check는 저장소 OpenAPI를 변경하지 않고 비교한다. UTF-8/LF·ai-logs의 -text/-merge 정책을 유지한다.

## 7. AI 로깅 보완과 제출 검증

검토 기준에서는 Claude 부속 .meta.json 재작성 감지 3건이 있었고 Codex hook 실행은 미확인이었다. 코드 착수 때 다시 읽기 전용 상태를 확인한다. 원본이 정상적으로 갱신되는 메타데이터인지 실제 손상인지 먼저 조사한다.

- transcript JSONL의 순서·앞부분 불변 검사는 유지한다. 부속 파일 갱신을 다루기 위해 원문·기존 스냅샷을 덮어쓰거나 검사 전체를 해제하지 않는다.
- 정상 변경되는 메타데이터라면 과거 사본과 새 사본을 구별해 보존할 수 있는 방식을 D14에서 승인한 뒤 구현한다. 세션 전체가 계속 보류되는 경로, 재실행·동시 실행·손상 파일을 검사한다.
- Codex 신뢰 설정과 실제 hook 실행을 구분한다. 변경한 hooks 설정은 신뢰 절차와 실제 프롬프트/종료 이벤트로 검증한다. 미실행이면 자동 로깅 정상이라고 표시하지 않는다.
- 일반 개발의 경고 허용과 최종 제출의 완전성 통과 조건을 구분한다. 최종 제출 대상 SHA와 세션별 수집 기준 시점을 기록하고, 모든 AI 턴 종료 후 원본 꼬리까지 확인한다.
- develop 스냅샷의 master 포함·동일성, 정책 변경 후 재검사, 보류 해소 뒤 전체본 수집, 이미 커밋된 사본의 비밀값 검사를 확인한다.
- 새 가짜 키·토큰은 실행 중 생성한다. 실제 보류 값은 사용자 판정 없이 허용하지 않으며 원문을 출력하지 않는다.

필요한 로깅 수정이 승인 범위를 넘으면 별도 이슈로 분리하고 최종 제출 영향은 남긴다. 제출 조건이 해결되지 않았는데 로그 제출 완료로 표시하지 않는다.

## 8. 성능: 측정 후 선택

기존 P-01~P-13을 추적하되 일괄 적용하지 않는다. 기준 환경, 데이터 분포, 데이터 수, 페이지·정렬, 동시성, 준비 요청, 표본 수, 처리량, p50/p95, 오류율, CPU·메모리·스레드·DB 커넥션을 기록한다. 정상과 그룹 지연/중지 상태를 구분한다.

## 9. 완료 기준과 커밋

1. 승인된 응답과 실제 JSON이 모든 깊이에서 일치하며, 정의 외 필드의 삽입을 검사기가 실제 검출한다.
2. 기존 페이지 설정·정렬·단일 소속·시각·code·트랜잭션·재시도·서비스 독립성을 보존한다.
3. 계약·계층·DB·연동·실행 테스트의 실패/오류/예상하지 않은 건너뜀이 없다. 테스트 이동 전후 누락이 없다.
4. 전체 build, 두 서비스 OpenAPI 검사, 루트 Compose 실제 HTTP 연동, Swagger의 멤버 및 그룹 실행을 검증한다. fixture·가짜 HTTP·실제 제공자 검증을 구분한다.
5. 적용된 코드와 api.md·정책·ADR·공유 JSON·README가 일치한다. api-review.md는 적용 완료 또는 이력으로 정리한다.
6. 성능은 전후 결과 또는 변경하지 않은 근거를 기록한다. 관측 로그가 요청·업무·원격·예외 흐름을 연결한다.
7. AI 로깅의 현재 상태와 최종 제출 기준 충족 여부를 별도로 명시한다. 모든 기록이 포함됐다는 주장은 제출 SHA·수집 범위 검증이 있을 때만 한다.

커밋 단위: 기준·인계 확인 → 응답 계약 구현 → 승인된 보안 → 테스트 이동만 → 테스트·구조 보완 → 문서 검사·명세 → 승인된 로깅 보완 → 측정 기반 개선 → 최종 검증 기록. 실제 변경이 없는 단계는 빈 커밋을 만들지 않는다.

메시지는 [REVIEW-002] 제목, 빈 줄, 두 칸 들여쓴 작업 내용과 공통 기여자 규칙을 따른다. 변경한 코드의 포맷과 필요한 검증을 마친 뒤 공통 build 검사를 수행한다. 정상 통과 후 변경·실패·미해결 우려 없이 같은 검사를 불필요하게 반복하지 않는다.

AI 턴 중 Git 변경을 직접 수행하지 않는다. 승인된 커밋·단계 로그는 기존 예약 기능을 사용하고 실제 SHA를 확인한다. master 병합·push, push-develop, merge-feature, turns resolve는 사용자 절차다.

feature에서 구현·검증 → develop 병합·실제 검증 → 문제 시 resume으로 feature 보완·재병합 → develop 로그만 master 동기화 → 검증된 feature를 master에 --no-ff 병합한다. develop 전체 병합·force·amend·과거 로그 편집은 하지 않는다.
