## 사용자 요청 요약

문서 정리와 계약 확정은 REVIEW-001에서 먼저 수행한다. REVIEW-002에서는 그 결과에 맞춰 소스코드와 테스트를 수정한다. 두 작업의 브랜치·검증·커밋을 구분하고, 확정된 response 외의 내용이 목록·상세에 노출되지 않게 한다.

## 착수 조건

- REVIEW-001이 develop 검토를 거쳐 master에 병합·push되어 있어야 한다.
- 최신 master에서 브랜치를 만들고 REVIEW-001의 최종 인계 문서·기준 커밋을 기록한다.
- 응답 필드·null·페이지·오류·중계 범위가 확정되어 있어야 한다. 선택적인 정책 변경은 승인 또는 현행 유지로 결정한다.
- API 계약의 최종 소유자는 각 서비스 docs다. 계획의 예시나 실제 코드에서 기대 응답을 역으로 만들어 승인된 계약을 대체하지 않는다.

## 포함·제외

포함: 승인된 API 계약 구현, 출력 필드 제한, 멤버-그룹 연동·중계, 테스트 보완·구조 정리, 필요한 문서 검사 자동화, 승인된 보안·로깅 보완, 측정에 근거한 성능 개선, 실제 실행·Swagger·로그 보존 검증.

제외: 미승인 DNS·로그 수준·회로 차단 도입(JWT·중복 처리는 아래 추가 요청으로 승인), 새 쓰기 API·다중 소속 기능·게이트웨이·공유 런타임 모듈, 이유 없는 DB 변경, 과거 로그·커밋 수정, 전체 develop의 master 병합.

문서 단계에서 보류된 요구를 암묵적으로 구현하지 않는다. 발견한 계약 변경은 소유 문서와 결정 기록을 먼저 보완한 뒤 해당 구현을 진행한다. master 반영은 사용자 절차를 따른다.

## 추가 요청 (2026-11-06)

필수 요건 전체 검토 뒤 사용자가 다음을 요청했다. 결정 내용은 [승인 계약 2차](approved-contract.md#2차-승인-2026-11-06)가 소유한다.

- page는 제거하지 않는다(클라이언트가 알아야 함). 대신 응답 상태 코드를 4xx 중심으로 세분화하고 Swagger에 노출한다.
- summary 중복 ID는 로그로 남기며 중복된 ID도 원문으로 남긴다.
- JWT는 권장안대로 하되, 커밋되지 않는 `secrets/` 대신 프로젝트 init 때 키를 생성해 local Swagger 자동 토큰을 처리한다.
- HEAD·OPTIONS와 POST·PUT·PATCH를 모두 막는다. 제공 API는 GET뿐이다.
- MEMBER-001·GROUP-001 문서에서도 `groups[]`를 걷어내 문서 정책을 통일한다.
