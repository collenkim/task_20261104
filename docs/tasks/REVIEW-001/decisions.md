# REVIEW-001 결정과 승인 상태

| 항목 | 내용 |
| --- | --- |
| 분류 | 작업 결정표 |
| 상태 | 문서 분류·응답 제한 요구 확정. 응답 개정안과 선택 정책은 사용자 확인 대기 |
| 기준 | 2026-11-05, master bc3ec02에서 만든 feature/REVIEW-001 |
| 계획 | [REVIEW-001](plan.md), [REVIEW-002](../REVIEW-002/plan.md) |

사용자가 요청한 **정의된 응답 외 필드 비노출**은 확정 요구다. 어떤 필드를 정의에 남길지와 중계의 계약 위반 처리 방식은 별도 결정이다. 제안을 현행 계약이나 승인된 정책으로 취급하지 않는다. 답변이 없으면 승인으로 간주하지 않는다.

| ID | 주제 | 상태·결정 | 적용·보류 시 동작 |
| --- | --- | --- | --- |
| D1 | summary 중복 ID | 확인 대기. 기존 400을 중복 제거 후 성공으로 바꾸는 안 | 원래 입력 수 1~100 및 모든 값 형식 검사 후 제거. ID 원문 로그 대신 반복 개수·요청 내 위치 제안. 승인 전 400 유지 |
| D2 | 멤버 그룹 표현 | 확인 대기. 목록 group 이름·permission, 상세 단일 group, 미소속 null 제안 | [멤버 개정안](../../../services/member-service/docs/api-review.md). 승인 전 groups 배열 현행 유지 |
| D3 | 감사·소속 시각 | 확인 대기. 공개 createdAt·createdBy 제거, group.joinedAt을 group.registeredDate로 표현하는 안 | DB 감사 정보는 유지. D2와 함께 정확한 응답 표 승인 필요 |
| D4 | 멤버 JWT | 확인 대기. Resource Server·서명·iss·aud·exp·scope 검증 제안 | 승인 전 사용자 인증 없음 유지. 승인 시 ADR-006을 새로 작성하고 오류·경로별 권한까지 확정 |
| D5 | 테스트 토큰 | D4 채택 시 결정. 단위·통합 테스트 실행 중 키/토큰 생성, 실행 검증은 secrets 파일 참조 제안 | 완성된 비밀값을 소스·출력에 넣지 않는 기존 규칙 유지. 만료·재발급·교체 절차 필요 |
| D6 | 그룹 Swagger 중계 | 기능 유지 확정. local 한정·JWT·별도 권한은 확인 대기 | 현재 모든 프로필의 두 고정 GET 중계 유지. 그룹 직접 포트와 내부 키는 브라우저에 공개하지 않음 |
| D7 | 문서 분류 | 사용자 요청으로 확정 | common은 공통 기준, tasks는 요청·계획, verification은 증거. 서비스 계약은 서비스 docs |
| D8 | 주소 | DNS 확대 미승인 | 숫자 IP:port 유지. 다른 컨테이너/서버 배포와 DNS 지원은 서로 다른 조건 |
| D9 | 계약 공유 | 기존 OpenAPI 산출물 공유 유지 | 생성 클라이언트는 소비자 소유. 향후 계약 대조는 버전·해시 고정 산출물 또는 루트 통합 검사. 서비스 단독 테스트가 다른 서비스 소스 트리를 요구하지 않음 |
| D10 | 과거 요청 | 원래 요구·검증 보존, 현재 문서와 구분 | 과거 본문을 새 요구로 소급 작성하지 않음. 대체 상태와 현재 기준 링크 추가 |
| D11 | 요청 재구성 | 이번 문서 정리 범위 | SETUP·LOG 요청서에 사후 작성 표시·출처·확인 한계 기록 |

| D13 | 로그 | 이전 사용자 결정 유지 | 요청 진입·업무·DB·외부 호출·재시도 INFO, 예외 ERROR. 4xx 수준 변경·한 줄로 축소는 별도 승인 필요 |
| D14 | AI 로그 완전성 | 원본·기존 스냅샷 보존 및 최종 완전성 확인은 확정. 부속 메타데이터 보존 방식은 조사·승인 대기 | 일반 개발 push 경고 정책과 최종 제출 통과를 구분. meta.json 보류를 숨기거나 원본 수정 금지 |
| D15 | 정의 외 응답 | 비노출은 사용자 확정. 중계 추가 필드 발견 시 500 INTERNAL_ERROR로 차단하는 방식은 제안 | 모든 출력 깊이의 정확한 필드 검사 필요. 내부 소비자 확장 허용과 공개 출력은 분리 |

확정 근거는 현재 대화의 문서/코드 브랜치 분리, 정의된 response만 노출, 최소 설치 프로그램 안내 요청과 기존 GROUP-001의 단일 소속·기존 상세 6필드·권한 code·시각·로그 요구다. 최초 통합 계획의 권장 문구 자체를 승인 근거로 쓰지 않는다.

## 확인이 필요한 핵심 응답 변경

D2·D3는 묶어서 확인한다. 목록 항목은 id/name/group/permission, 상세는 id/name/email/address/registeredDate/group이다. 상세 group은 id/name/registeredDate/pricing/permission이다. 페이지 정보는 유지하며 group은 미소속일 때 null이다. 상세의 그룹 가입일·과금은 현재 소비자 허용 범위를 보존해 키는 필수, 값은 null 가능으로 제안한다.

그룹 상세는 memberId/groupId/groupName/registeredDate/pricing/permission의 기존 평면 단일 객체를 유지한다. 멤버의 group 객체와 그룹 원본 상세를 같은 DTO로 공유하지 않는다.

## 적용 순서

문서 검토 → 결정표와 서비스 개정안 승인 → REVIEW-001 검증·develop 검토·사용자 master 반영 → master에서 REVIEW-002 생성 → 승인 항목 구현·테스트·현재 문서/생성 OpenAPI 갱신 순서다. 미승인 핵심 계약이 남으면 코드 착수 가능으로 표시하지 않는다.
