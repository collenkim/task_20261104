사용자가 요청한 **정의된 응답 외 필드 비노출**은 확정 요구다. 어떤 필드를 정의에 남길지와 중계의 계약 위반 처리 방식은 별도 결정이다. 제안을 현행 계약이나 승인된 정책으로 취급하지 않는다. 답변이 없으면 승인으로 간주하지 않는다.

확정 근거는 현재 대화의 문서/코드 브랜치 분리, 정의된 response만 노출, 최소 설치 프로그램 안내 요청과 기존 GROUP-001의 단일 소속·기존 상세 6필드·권한 code·시각·로그 요구다. 최초 통합 계획의 권장 문구 자체를 승인 근거로 쓰지 않는다.

2026-11-06 로그 내용 후보 후속 승인: 사용자는 검토한 29종의 정확한 값만 허용하고 나머지 2종을 마스킹하도록 승인했다([적용·검증 기록](../../verification/REVIEW-002/log-holds.md)). 이어 과거 사본 해시 일치와 정상 종료 표시 추가가 확인된 뒤 “그렇게 수정하고, 마저 최종 제출이 진행될 수 있도록 진행해줘”라고 요청하여 D14의 좁은 메타데이터 이력 보존을 승인했다. 과거 live 사본은 교체 전에 불변 보관하고, 제출 스냅샷에는 현재 정책으로 마스킹한 이전·현재 버전을 함께 담는다. 임의의 메타데이터 수정 허용이나 원본·기존 스냅샷 수정 승인은 아니다.

2차 확정(2026-11-06, REVIEW-002): 사용자가 page 응답 유지, 4xx·5xx 상태별 오류 코드표(400 `INVALID_PARAMETER`~504 `GATEWAY_TIMEOUT`), 형식 400/의미 422 구분, 세부 원인의 `type` URN 표현, 중복 ID 원문 로그, JWT 권장안과 init 키 생성, HEAD·OPTIONS·POST·PUT·PATCH 차단(GET 전용), MEMBER-001·GROUP-001 문서의 `groups[]` 제거를 결정했다. 상세는 [REVIEW-002 승인 계약](../REVIEW-002/approved-contract.md#2차-승인-2026-11-06)에 있다.

후속 확정: 사용자가 D2·D3 단일 group·감사 필드 제외·가입일 분리와 D15 정의 필드 선별을 승인했다. 일괄 500 제안은 폐기하고 원인별 502/503/504로 구분한다. [최종 승인 계약](../REVIEW-002/approved-contract.md)이 이전 확인 대기·제안 문구보다 우선한다.

## 확인이 필요한 핵심 응답 변경

D2·D3는 묶어서 확인한다. 목록 항목은 id/name/group/permission, 상세는 id/name/email/address/registeredDate/group이다. 상세 group은 id/name/registeredDate/pricing/permission이다. 페이지 정보는 유지하며 group은 미소속일 때 null이다. 상세의 그룹 가입일·과금은 현재 소비자 허용 범위를 보존해 키는 필수, 값은 null 가능으로 제안한다.

그룹 상세는 memberId/groupId/groupName/registeredDate/pricing/permission의 기존 평면 단일 객체를 유지한다. 멤버의 group 객체와 그룹 원본 상세를 같은 DTO로 공유하지 않는다.

## 적용 순서

문서 검토 → 결정표와 서비스 개정안 승인 → REVIEW-001 검증·develop 검토·사용자 master 반영 → master에서 REVIEW-002 생성 → 승인 항목 구현·테스트·현재 문서/생성 OpenAPI 갱신 순서다. 미승인 핵심 계약이 남으면 코드 착수 가능으로 표시하지 않는다.
