## 사용자 요청 요약

- REVIEW-001은 문서 작업부터 진행한다. 코드 작업은 REVIEW-002로 분리한다.
- 두 브랜치의 작업 범위·순서·검증·완료 조건을 각각 계획으로 관리한다.
- 멤버·그룹의 목록과 상세에는 확정된 응답 필드 외의 내용을 노출하지 않는다.
- 실제 코드와 실행 응답을 확인하고, 문서에만 남은 내용인지 실제 동작인지 구분한다.
- 공통 문서는 프로젝트 docs, 서비스 소유 계약·정책·엔티티 문서는 해당 서비스 docs에서 관리한다.
- README에 프로젝트 구동에 필요한 최소 설치 프로그램과 버전·실행 조건을 명시한다. Docker 일괄 실행, IDE/로컬 빌드, AI 로그·자동 검증에 필요한 도구를 구분한다.
- 기존 master → feature → develop 검증 → feature → master 흐름과 AI 로그 보존 규칙을 유지한다.

## 범위의 구분

포함: 요구사항·검토 결과·계획, 문서 분류와 이동, README·색인·링크, 현재 정책의 사실관계 정리, 서비스별 계약 개정안, 결정 및 후속 구현의 인수 조건.

제외: Kotlin·테스트 코드, SQL·시드, Gradle·Compose·애플리케이션 설정, OpenAPI JSON 재생성, 로깅 스크립트·hook 수정, 성능 개선 구현. 기존 검증 명령의 실행은 구현 변경과 구분한다.

최초 통합 review-plan의 권장안 전체를 승인한 것으로 간주하지 않는다. 그룹 표현, 감사 필드, JWT, 중복 ID, DNS, 로그 수준, 회로 차단 등은 현재 결정과 신규 제안을 구분하여 문서화한다. 확정되지 않은 선택을 코드에 적용하지 않는다.

이 문서는 사용자 요청을 요약한 작업 기록이다. 과거 사용자 발언을 새로 만든 인용문으로 제시하지 않는다. API 필드의 소유 문서는 서비스별 API 정의서이며, 이 요청서에 JSON 계약을 중복 정의하지 않는다.
