   200	예: 저장 시각 2026-08-15T04:00:59.123456Z → 응답 2026-08-15 13:00. 응답 변환 뒤에도 DB 값은 그대로 보존한다.
   201	
   202	- 멤버 member.registered_at → 멤버 registeredDate: 멤버 가입 시각.
   203	- 멤버 member.created_at → 멤버 createdAt: 멤버 행 생성 시각.
   204	- 그룹 group_membership.joined_at → 그룹 registeredDate: 해당 그룹 가입 시각.
   205	- 멤버 상세의 groups[].joinedAt: 그룹이 제공한 가입 시각을 같은 형식으로 전달.
   206	- 그룹 소속 시각을 멤버 가입 시각으로 대체하거나 그 반대로 사용하지 않는다.
   207	- 원격 시각에는 이미 초 이하가 없으므로 전용 값 객체 또는 LocalDateTime 등으로 분 정밀도를 드러낸다. 내부 Instant로 변환해야 한다면 정밀도가 분 단위라는 의미를 명시하고 원본 정밀도 보존이라고 주장하지 않는다.
   208	- 공통 API 규칙의 UTC RFC 3339 업무 응답 규정을 변경한다. HTTP 표준 헤더나 애플리케이션 로그·AI 원본 세션 시각까지 분 단위로 변경하지 않는다.
   209	- OpenAPI는 type:string, 패턴·한국 시간 설명·예제를 사용한다. 이 문자열에 format:date-time을 붙이지 않는다. 정규식 검증 외에 실제 달력 날짜의 유효성을 테스트한다.
   210	
   211	### 4.1 기존 멤버 DB 전환
   212	
   213	현재 멤버 V2의 registered_at, created_at은 DATETIME(6)이다.
   214	
   215	- 이미 적용한 V2를 수정하지 않는다. 구현 시 다음 미사용 버전(현재 기준 V3)에 TIMESTAMP(6) 전환 마이그레이션을 추가한다.
   216	- 기존 값이 UTC라는 현재 정책을 확인하고, 전환 세션 시간대를 UTC로 고정한다.
   217	- 전환 전 NULL·zero date·대상 타입 지원 범위 밖 값이 없는지 검증한다. 잘못된 값을 자동 보정·삭제하지 않는다.
   218	- MariaDB의 DDL 롤백을 가정하지 않는다. 실제 데이터 전환 전 백업·복구 절차와 적용 전 점검을 문서화한다.
   219	- 기존 V2 + 합성 데이터 DB에서 신규 마이그레이션을 적용해 행 수, 키, 모든 시각의 초·마이크로초가 동일한지 검사한다.
   220	- 신규 DB의 전체 migrate 경로도 검사한다. 볼륨 초기화나 Flyway clean을 전환 방법으로 삼지 않는다.
   221	- 두 서비스의 ddl-auto=validate와 실제 INSERT/SELECT 왕복을 검증한다.
   222	- 가입·생성 시각이 다른 열 UPDATE만으로 자동 갱신되지 않도록 DDL을 명시하고 검증한다.
   223	
   224	근거: [MariaDB TIMESTAMP](https://mariadb.com/docs/server/reference/data-types/date-and-time-data-types/timestamp). 소수점 정밀도와 연결 세션 시간대, 타입 범위를 함께 확인한다.

   227	
   228	### 5.1 테이블
   229	
   230	| 테이블 | 열 | 타입/제약 |
   231	| --- | --- | --- |
   232	| user_group | id | CHAR(10), ascii_bin, PK |
   233	| user_group | name | VARCHAR(100), NOT NULL |
   234	| user_group | pricing | VARCHAR(20), ascii_bin, NOT NULL; code 저장 |
   235	| user_group | created_at / created_by | TIMESTAMP(6) / VARCHAR(50), NOT NULL |
   236	| group_membership | id | BIGINT AUTO_INCREMENT PK |
   237	| group_membership | group_id | CHAR(10), ascii_bin, NOT NULL, 같은 DB의 user_group FK |
   238	| group_membership | member_id | CHAR(10), ascii_bin, NOT NULL, 외부 ID만 저장. 멤버 DB FK 없음 |
   239	| group_membership | permission | VARCHAR(20), ascii_bin, NOT NULL; code 저장 |
   240	| group_membership | joined_at / created_at | TIMESTAMP(6), NOT NULL |
   241	| group_membership | created_by | VARCHAR(50), NOT NULL |
   242	
   243	- UNIQUE(member_id), UNIQUE(group_id, member_id).
   244	- member_id 고유 인덱스로 멤버별 조회와 복수 소속 입력 차단을 보장한다. 중복 보조 인덱스를 추가하지 않는다.
   245	- 그룹의 다음 미사용 마이그레이션 버전(현재 기준 V2)에 업무 테이블을 추가한다.
   246	- 비밀값·실제 개인정보를 마이그레이션에 포함하지 않는다.
   247	
   248	### 5.2 코드
   249	
   250	| enum | code | 내부 codeName 제안 |
   251	| --- | --- | --- |
   252	| GroupPricingType | Free / Advanced / Premium | 무료 / 어드밴스드 / 프리미엄 |
   253	| GroupPermissionType | Viewer / Editor / Admin | 조회자 / 편집자 / 관리자 |
   254	
   255	- 모든 코드 enum은 code, status, codeName, description을 가진다.
   256	- status는 코드의 사용/폐기 상태다. ACTIVE/DEPRECATED를 사용하며 소속 자체의 활성 상태와 혼용하지 않는다.
   257	- codeName·description은 한국어로 정의하고 내부 관리에 사용한다. 응답 필드로 노출하지 않는다.
   258	- 과금·권한의 code는 대소문자를 구분한다. DB에는 명시적 AttributeConverter로 code를 저장하며 순번·상수 이름을 저장하지 않는다.
   259	- 알 수 없는 저장 code는 데이터 오류다. API 500과 정제된 ERROR 로그로 처리한다.
   260	- CHECK를 생략하는 안에서는 SQL 직접 입력까지 변환기가 보호한다고 설명하지 않는다. 잘못된 SQL 입력을 읽을 때 실패하는 검증을 추가한다.
   261	- 멤버는 그룹 enum을 직접 의존하거나 복제하지 않고 code 문자열을 다룬다. 신규 code가 들어와도 폐쇄형 enum 파싱 때문에 실패하지 않도록 소비자 계약을 유지한다.
   262	
   263	### 5.3 local 시드
   264	
   265	- 그룹 local 프로필을 구성하고 Flyway locations에 migration과 db/seed/local을 모두 명시한다.
   266	- R__seed_group.sql은 최초 적용과 체크섬 변경 시에만 실행한다. 무변경 재기동은 재실행하지 않는다.
   267	- 고정 합성 데이터만 사용하고 CURRENT_TIMESTAMP나 무작위 값으로 매번 바뀌게 만들지 않는다.
   268	- created_by가 정확히 seed인 행만 허용된 업무 필드를 갱신한다. 생성 시각·생성자와 비시드 행은 보존한다.
   269	- 매핑 행은 고정 ID와 (group_id, member_id) 고유 제약 충돌을 함께 확인한다. 비시드 충돌을 무조건 upsert로 덮어쓰지 않는다.
   270	- 그룹은 세 과금 유형, 소속은 세 권한 유형, 미소속 멤버, 인원이 없는 그룹을 포함한다.
   271	- 정상 시드와 멤버 fixture는 멤버당 최대 한 그룹이다. 같은 멤버의 다른 그룹 입력은 실제 DB에서 거부되는지 검증한다. 조회 다건 예외는 별도 포트 대역으로 재현한다.
   272	- 기존 멤버 fixture와 local 시드는 새 그룹 계약의 값·코드·시각 형식으로 정렬한다. 두 DB 사이 자동 동기화는 가정하지 않는다.
   273	- 빈 그룹은 memberIds 기반 summary에 나타나지 않으므로 저장소 시험에서 별도로 확인한다.
   274	- 기본 프로필에는 local 시드와 fixture를 적용하지 않는다. 시드 항목 삭제를 실제 행 자동 삭제로 해석하지 않는다.
   275	- 최초/재기동/체크섬 변경/감사 정보 보존/비시드 보호/충돌 보고를 실제 MariaDB로 검사한다.

   277	## 6. CQRS와 멤버 연동 변경
   278	
   279	### 6.1 그룹 계층
   280	
   281	~~~text
   282	presentation/query/
   283	  GroupQueryApi, GroupQueryController
   284	  request/, response/, mapper/
   285	presentation/error/
   286	application/query/summary/
   287	application/query/detail/
   288	application/port/input/
   289	application/port/output/
   290	application/model/
   291	application/exception/
   292	domain/
   293	infrastructure/persistence/group/
   294	infrastructure/configuration/
   295	infrastructure/logging/
   296	~~~
   297	
   298	- Controller → 입력 포트, Handler → 출력 포트·순수 조회 모델·domain 방향을 유지한다.
   299	- application에서 infrastructure·presentation·JPA·Spring Data·Servlet·Jackson·OpenAPI를 참조하지 않는다.
   300	- 엔티티·HTTP DTO·조회 모델을 분리한다. HTTP와 DB 구현을 바꾸어도 업무 코드가 따라 바뀌지 않도록 한다.
   301	- 조회 전용이므로 비어 있는 command 계층이나 사용하지 않는 추상화를 만들지 않는다.
   302	- Handler의 업무 로그는 SLF4J 등 최소 로깅 인터페이스로 기록한다. MDC/HTTP/저장소 구현 의존성을 주입하지 않는다.
   303	
   304	### 6.2 조회와 트랜잭션
   305	
   306	- Jpa Reader 안에서만 읽기 트랜잭션을 열고 닫는다. Handler는 트랜잭션을 유지하지 않는다.
   307	- summary: 소속·그룹 projection 조회 1회 + 해당 그룹의 전체 인원 집계 1회. 결과가 없으면 집계를 생략한다.
   308	- ID 1개와 100개, 서로 다른 멤버가 속한 그룹의 수에 관계없이 쿼리 최대 2회. 엔티티 lazy loading이나 그룹별 count 반복을 만들지 않는다.
   309	- 두 쿼리는 같은 트랜잭션에서 REPEATABLE READ 일관 읽기를 사용하도록 명시한다. readOnly만으로 격리 수준이 보장된다고 가정하지 않는다.
   310	- 중간에 다른 연결이 소속을 변경해도 행과 집계가 같은 스냅샷을 보는지 실제 동시성 시험으로 확인한다.
   311	- detail은 0건/1건/2건 이상을 판별할 수 있게 조회한다. 2건 이상이면 Handler가 GroupMembershipAmbiguousException을 발생시킨다. 임의 limit 1로 숨기지 않는다.
   312	- summary도 한 memberId가 서로 다른 그룹에 반복되는 경우 같은 무결성 예외로 처리한다.
   313	- DB 밖에 나온 모델에서 순수 묶기·정렬·응답 변환을 수행한다.
   314	
   315	### 6.3 멤버 소비자
   316	
   317	현재 목록·상세가 같은 findByMemberIds를 사용하므로 인프라 변경만으로 완료된다고 설명하지 않는다.
   318	
   319	- 목록용 일괄 조회와 상세용 단일 소속 조회를 의미가 분명한 포트/메서드로 구분한다.
   320	- 페이지 크기 1을 상세 조회로 판단하지 않는다. Handler가 필요한 기능을 명시한다.
   321	- 목록은 한 페이지 ID를 모아 summary 한 번, 상세는 group/{memberId} 한 번 호출한다.
   322	- permissionName을 얻기 위한 추가 summary 호출은 없다.
   323	- 멤버 DB 조회 트랜잭션이 끝난 뒤 원격 호출한다. DB 커넥션을 잡고 HTTP 대기·재시도를 하지 않는다.
   324	- summary 정상 응답은 요청 ID별 빈 소속으로 초기화한 뒤 반환 행을 합친다. 응답에 없는 ID는 정상 미소속이다.
   325	- 요청하지 않은 ID·중복 그룹/소속·잘못된 타입·필수 필드 누락은 계약 오류다.
   326	- 상세의 memberId가 요청과 일치해야 한다. 정확한 미소속 404만 빈 groups로 변환한다.
   327	- 멤버 공개 groups 배열 형태는 유지하되 현재 목록·상세의 정상 결과는 멤버당 0~1개 소속이다. 복수 소속 응답은 계약 오류로 거부한다. 그룹이 다건 예외로 반환한 500은 기존 정책에 따라 멤버 503으로 처리한다.
   328	- 멤버 목록·상세의 permissionName을 제거한다. permission code는 그대로 전달한다.
   329	- 멤버 상세의 registeredDate·createdAt·groups[].joinedAt은 4절 형식으로 변경한다.
   330	- page/size/sort 검증, 이름 정렬과 ID 보조 정렬, offset 검증, spring.data.web.pageable 설정 블록을 보존한다.
   331	- fixture/HTTP 공급자에 동일한 애플리케이션 의미를 적용한다. fixture를 새 HTTP DTO의 세부 구조에 불필요하게 묶지 않는다.
   332	- 루트 일괄 실행은 실제 그룹을 사용하는 http 모드로 명시한다. 서비스 단독 local fixture와 기본 프로필의 http 요구는 별도 문서화한다.
   333	
   334	### 6.4 기존 재시도 보존
   335	
   336	- 연결 2초·읽기 3초, 추가 재시도 기본 1회, 기존 설정 범위와 검증을 유지한다.
   337	- 재시도는 GET/HEAD의 응답 수신 전 연결 실패·시간 초과에 한한다.
   338	- 지수 백오프 + Full Jitter, cap·횟수·인터럽트 복구를 유지한다.
   339	- 4xx/5xx 응답, JSON/날짜/계약 오류는 새로 재시도 대상에 넣지 않는다.
   340	- 요청 단위 로그와 시도 단위 로그를 구별하고 다른 계층에 재시도를 중첩하지 않는다.
   341	- 그룹 장애여도 멤버는 기동하며, 그룹 정보가 필요한 API가 정해진 오류를 반환한다.

   343	## 7. 최소 내부 인증과 실행 설정
   344	
   345	- X-Internal-Service-Id + X-Internal-Service-Key를 각각 정확히 한 값으로 받는다.
   346	- 등록 서비스 ID와 그 서비스의 키 조합을 검증한다. 서비스 ID만으로 신뢰하지 않는다.
   347	- 키는 기존 고정 길이 해시·상수 시간 비교 방식을 재사용한다. 두 호출자의 키를 서로 바꾸어도 통과하지 않아야 한다.
   348	- 등록 호출자가 없거나 키가 비면 기동 실패. 호출자 ID·CIDR 설정 오류도 시작 시 확인한다.
   349	- CIDR은 선택 사항이며 실제 remoteAddr로 검사한다. X-Forwarded-For는 신뢰하지 않는다.
   350	- health와 /error의 기존 예외 유지, /v3/api-docs는 내부 인증 필요, 그룹 Swagger UI 비활성 유지.
   351	- 숫자 IP:명시적 포트 검증·IPv4/IPv6 지원과 그룹 포트 미공개를 유지한다.
   352	- 호출자 추가는 등록 설정·키 파일로 가능하게 한다. 사용자 인증·JWT·OAuth를 도입하지 않는다.
   353	
   354	설정 보완:
   355	
   356	1. 기존 키 파일을 member-service 호출자의 키로 재사용할 수 있게 구성한다. 비밀값은 읽거나 출력하지 않는다.
   357	2. Compose secret target뿐 아니라 bootRun·IDE의 configtree 파일명/속성 바인딩도 함께 맞춘다.
   358	3. 생성·교체 도구, 그룹 caller map, 멤버 groupRestClient, 명세 전달 클라이언트가 같은 설정 계약을 따른다.
   359	4. 대시가 포함된 member-service map key, 키 미설정·빈 키·다른 호출자 키를 실제 Spring 바인딩 시험으로 확인한다.
   360	5. 루트 Compose, 서비스 단독 Compose, bootRun, IDE의 주소·프로필·키 경로·선택 CIDR을 실행 표로 관리한다.
   361	6. 루트의 고정 IP나 IDE의 IPv6 loopback 등 실제 peer 주소와 CIDR이 일치하는지 확인한다.
   362	
   363	## 8. 요청부터 예외까지 추적하는 로그
   364	
   365	### 8.1 공통 규칙
   366	
   367	두 서비스에 같은 필드 규칙을 적용한다. 런타임 공통 서비스 모듈을 만들지는 않는다.
   368	
   369	| 위치/사건 | 기본 수준 | 기록할 내용 |
   370	| --- | --- | --- |
   371	| 요청 진입 request.received | INFO | requestId, service, method, 안전한 경로 식별자, 수신 시각 |
   372	| 인증 결과 internal.auth.completed | INFO | 등록된 caller 또는 unknown, 허용/거부, 정해진 사유 코드 |
   373	| 업무 시작 business.started | INFO | operation, 입력 건수·페이지 번호·적용 크기 등 비식별 정보 |
   374	| 저장소 경계 query.started/completed | INFO | queryName, 결과 건수, durationMs. SQL·바인딩 값 제외 |
   375	| 업무 단계 business.progress | INFO | member.loaded, membership.lookup, result.assembled 등 정해진 stage |
   376	| 그룹 호출 remote.started/completed | INFO | dependency=group-service, operation, callId, 상태·건수·durationMs |
   377	| 실제 시도 remote.attempt.started/completed | INFO | callId, attempt, 결과 상태, durationMs |
   378	| 재시도 예약 remote.retry.scheduled | INFO | attempt, nextAttempt, delayMs, 정제된 reason |
   379	| 업무 정상/미소속 결과 business.completed | INFO | outcome, 결과 건수, durationMs |
   380	| 예외 처리 exception.handled / remote.failed | ERROR | operation, stage, 오류 code·예외 분류, callId/attempt, 정제된 원인 |
   381	| 요청 종료 request.completed | INFO | method, 최종 경로 템플릿, status, code, outcome, 전체 durationMs |
   382	
   383	- 기본 INFO이며 예외가 발생·처리되는 지점은 ERROR다. 예상 가능한 검증·미소속도 예외 경로로 처리했다면 ERROR 사건을 남기되 불필요한 전체 스택은 생략한다.
   384	- 인증 거부처럼 예외 없이 결정한 결과는 INFO로 기록한다. 예외를 던져 처리한 경우에는 ERROR 규칙을 따른다.
   385	- 요청 결과를 한 줄만 남기던 규칙은 폐기한다. 진입·업무·의존 호출·종료 사건을 함께 사용한다.
   386	- 각 사건의 책임 위치를 하나로 정한다. 같은 예외를 Reader, Handler, Controller에서 catch-log-rethrow하며 중복 기록하지 않는다.
   387	- 원격 실패는 시도 경계에서 ERROR로 기록할 수 있다. 최종 오류 매핑은 같은 callId와 최종 code로 연결하며 동일 예외의 스택을 다시 출력하지 않는다.
   388	- 예외 스택은 서비스 내 같은 실패에 한 번만 기록한다. 그룹과 멤버가 각자 실패를 기록하는 것은 서로 다른 서비스 경계의 사건이다.
   389	- 로그 시각은 시간대와 밀리초 이상 정밀도를 유지한다. 업무 API의 분 단위 문자열 규칙을 로그에 적용하지 않는다.
   390	- 애플리케이션 INFO를 기본으로 하되 ORM SQL·바인딩 값·HTTP wire 로그는 켜지 않는다.
   391	
   392	### 8.2 상관관계와 로그 안전성
   393	
   394	- 요청 필터는 내부 인증 필터보다 앞에서 실행한다.
   395	- X-Request-Id가 허용 문자와 길이를 만족하면 사용하고, 없거나 잘못되면 새 ID를 만든다.
   396	- 동일 requestId를 멤버 → 그룹 → 멤버 응답 헤더로 전달한다. 선택 기능이 아니라 이번 필수 구현 범위다.
   397	- 멤버의 논리적 그룹 호출마다 callId를 부여하고 재시도별 attempt를 구분한다. requestId는 전체 요청 동안 유지한다.
   398	- 최초 진입에서는 아직 매칭되지 않은 route를 pending으로 둘 수 있다. 종료 시 /api/group/{memberId} 같은 템플릿을 기록한다. 실제 경로 ID는 쓰지 않는다.
   399	- durationMs는 단조 증가 시계를 사용해 계산한다.
   400	- MDC는 finally에서 정리·복원한다. 비동기 사용 시 컨텍스트 전달·정리도 검증한다.
   401	- ERROR/ASYNC 재디스패치로 request.received/completed가 중복되지 않도록 한다. 인증 실패와 미매칭 경로도 종료 로그가 있어야 한다.
   402	- 키·전체 헤더·쿼리 문자열·본문·실제 멤버 ID·이름·이메일·주소·SQL 파라미터는 기록하지 않는다.
   403	- 예외 message/cause에 외부 본문·URL·SQL 값이 들어갈 수 있으므로 원문을 무조건 출력하지 않는다. 정해진 오류 분류와 정제된 스택을 사용한다.
   404	- 호출자 문자열·requestId는 검증한 값만 기록한다. 미등록 caller 원문을 로그에 넣지 않는다.
   405	- 로그는 반환 결과·기존 예외 전파·재시도 횟수를 바꾸지 않아야 한다.
   406	
   407	정상 요청의 추적 흐름:
   408	
   409	~~~text
   410	멤버 요청 진입
   411	 → 멤버 업무 시작
   412	 → 멤버 DB 조회 시작/완료 (트랜잭션 종료)
   413	 → 그룹 호출 시작/시도
   414	   → 그룹 요청 진입/인증
   415	   → 그룹 업무 시작/DB 조회/결합/완료
   416	   → 그룹 요청 종료
   417	 → 그룹 호출 완료
   418	 → 멤버 응답 결합/업무 완료
   419	 → 멤버 요청 종료
   420	~~~
   421	
   422	실패 시험에서는 위 흐름에 ERROR 사건, 재시도 예약 또는 최종 오류 매핑이 예상 위치에 나타나는지 확인한다.
   423	
   424	## 9. OpenAPI와 계약 공유
   425	
   426	- 기존 springdoc과 서비스별 OpenAPI 스냅샷을 재사용한다. 문서용 새 외부 서비스나 공유 런타임 DTO를 추가하지 않는다.
   427	- 그룹의 두 경로, summary의 반복 memberIds, 단일 상세의 기존 6개 필드, 오류별 응답을 명시한다.
   428	- 권한·과금의 code는 문자열로 표시한다. codeName·description·status를 응답 스키마에 추가하지 않는다.
   429	- 멤버 목록/상세의 permissionName을 스키마·예제·필수 목록에서 제거한다.
   430	- 두 서비스의 모든 해당 업무 시각 필드는 다음 규칙을 사용한다.
   431	
   432	~~~yaml
   433	type: string
   434	pattern: '^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}$'
   435	minLength: 16
   436	maxLength: 16
   437	description: 한국 시간(Asia/Seoul)의 분 단위 시각. DB에는 마이크로초까지 보존한다.
   438	example: '2026-08-15 13:00'
   439	~~~
   440	
   441	- 내부 인증 ID와 키는 AND다. 다음 두 스킴을 같은 security 항목에 둔다.
   442	
   443	~~~yaml
   444	security:
   445	  - internalServiceId: []
   446	    internalServiceKey: []
   447	~~~
   448	
   449	- 원본 그룹 명세에는 내부 인증 조건을 명시한다.
   450	- 멤버 전달 명세는 내부 주소·인증 스킴을 제거하고 servers=/internal-api/group으로 바꾼다. 그룹 두 GET의 Try it out을 활성화하며 요청서 8절의 상태/본문 보존과 제한을 따른다.
   451	- requestId 헤더를 명세에 추가하고, 생성·전파·반환 규칙을 설명한다. 키 예시는 실제 값으로 작성하지 않는다.
   452	- 인증 필터와 예외 처리기의 실제 ProblemDetail에 type/title/status/detail/instance/code 계약을 검사한다.
   453	- 실제 MockMvc 응답·예제·생성 스냅샷의 일치를 검사한다. 날짜 패턴만 맞고 달력이 잘못된 사례도 별도 검증한다.
   454	- 멤버 계약 공유 문서에 permissionName 삭제, 시각 형식 변경, 그룹 내부 API 교체를 명시한다.
   455	- 보안 스킴 AND 근거: [OpenAPI Security Requirement](https://spec.openapis.org/oas/v3.1.0#security-requirement-object).

   501	## 12. 구현 순서·커밋·브랜치
   502	
   503	1. 최신 master와 작업 폴더 상태를 확인하고 기존 자동화 절차로 feature/GROUP-001을 만든다. 이번 계획 작성 중에는 만들지 않는다.
   504	2. 확정된 단일 소속·다건 예외 정책에 따라 공통·서비스 계약, 오류·시각·로그 규칙을 먼저 맞춘다.
   505	3. 그룹 스키마/enum/Reader와 멤버 TIMESTAMP 전환을 구현하고 실제 DB로 검증한다.
   506	4. 그룹 summary·단일 상세·오류·local 시드를 구현한다.
   507	5. 멤버 의미별 포트·HTTP/fixture 공급자·DTO·시각 변환을 변경한다. paging 설정은 유지한다.
   508	6. 내부 인증 설정을 모든 실행 방식에 맞추고 두 서비스 로그·requestId 전파를 구현한다.
   509	7. OpenAPI/소비자/계층/트랜잭션 회귀를 확인하고 실제 http Compose 실행을 검증한다.
   510	8. feature에서 통과한 내용을 develop에 병합해 통합 검증한다.
   511	9. 문제가 있으면 기존 resume 절차로 같은 feature에 최신 master를 일반 merge하고 수정한 뒤 develop에 다시 병합한다.
   512	10. 검증된 feature만 기존 merge-feature 절차로 master에 병합한다. develop 전체를 master에 병합하지 않는다.
